# The UI subsystem

Widgets (panels, labels, buttons, check boxes, radio buttons, text fields, lists, sliders, progress bars) drawn on the **graphics layer** (layer 3, 640 x 300), driven by the mouse and the keyboard. Roadmap item 47 / section 15. Demo: `demos/ui.bas`. Window host only: the console host answers "Not available in the console host" (a text screen renderer is a later step).

## Layers of the implementation
- `font.[ch]` (no SDL): proportional fonts built from the 8 x 12 font (sans = ink columns shifted left plus one pixel gap, bold = double strike). `font_measure()`, `font_draw()`, `font_fit()`. Test: `fonttest1`.
- `ui.[ch]` (no SDL, no VM): the retained widget table (up to 192 widgets, ids chosen by the caller), theme, drawing of the changed parts only, hit testing, focus / Tab order, text editing, lists, sliders, modal panel, pop-up, an event queue of 64. It draws through a small canvas table (`ui_canvas_t`: box and pixel), so it is tested on a `gfxcore` bitmap. Test: `uitest1` (122 checks, pixel checks included).
- `gfxops.c` rows (group `UI`) and the extension word `UI` (`XF_UI`) in the parser; the host (`engine1999.c`, `host_ui_op()`) maps them to `ui.h`; the mouse comes from `mouse_get()` and the keys from `sdlscr_pollkey()` (escape sequences parsed with `keyseq_parse()`).

## Decisions taken (owner, 2026-11-01) and mine
- The UI owns the graphics layer; its theme uses the palette entries 224..239 of that layer (`UI_PALBASE`); the mouse pointer sprite stays in front; `UI OPEN` shows the pointer permanently.
- One form plus modal panels and pop-ups first; overlapping windows later. Retained widgets.
- Mine: widgets are drawn in creation order (z-order = order of creation); a **pop-up is a hidden list** that `UI POPUP id,x,y` shows (a click outside or Escape closes it with a cancel event); a **modal panel** (`UI MODAL id`) makes only the panel and widgets lying inside it react; events are polled with `UI("EVENT")` or delivered to a handler by `ON UI` (below).

## Statements
`UI OPEN`, `UI CLOSE`, `UI CLEAR`, `UI UPDATE`; `UI LABEL|BUTTON|CHECK|TEXT|PANEL id,x,y,w,h,text$`; `UI RADIO id,x,y,w,h,text$[,group]`; `UI TAB id,x,y,w,h,names$` (a **tab strip**: the names separated by `|`, drawn as tabs of a width that fits each name, the selected one raised and taller; the value is the number of the selected tab from 0, `UI VALUE id,n` selects without an event, a click or Left / Right on the focus selects and queues a change event whose value is the tab; the program shows and hides the widgets of its pages, e.g. with `UI SHOW`; the strip needs no space below it: its height is the tab height, 22 is a good one); `UI LIST|PROGRESS id,x,y,w,h`; `UI SLIDER id,x,y,w,h[,min]`; `UI SCROLL id,x,y,w,h[,page]` (a scroll bar: vertical when it is higher than wide; positions 0..100 until `UI RANGE id,min,max`; `UI PAGE id,n` sets the size of the visible part, which sizes the knob and the Page up / down step; events: change with the position); `UI REMOVE|FOCUS|CLEARLIST|MODAL id` (`MODAL 0` ends it); `UI CAPTION|ITEM id,text$`; `UI VALUE|ENABLE|SHOW id,n`; `UI RANGE id,min,max`; `UI POPUP id,x,y`; `UI GETTEXT id,a$`; `UI ITEMTEXT id,row,a$`.

## Functions
`UI("EVENT")` next event id (0 none; makes it current), `UI("KIND")`, `UI("VALUE")` of the current event, `UI("GET",id)`, `UI("COUNT",id)` rows of a list, `UI("FOCUS")`, `UI("OPEN")`, `UI("EVENTS")` (the number of events queued so far; what `ON UI` watches), `UI("PIXEL",id,x,y)`.
Event kinds: 1 click (button), 2 change (check, radio, slider, text field: the new length), 3 select (list row), 4 double click (or Return in a list), 5 Return in a text field, 6 cancel (Escape in a modal panel / pop-up, click outside a pop-up), 7 / 8 a canvas cell with the left / right button.

## ON UI
`ON UI GOSUB|GOTO target` / `ON UI OFF` (2026-11-05): a handler that runs between two statements whenever a widget has queued an event, so the main loop only has to call `UI UPDATE`. An event slot like `ON MOUSE` / `ON KEY` (`VM_UISLOT` 8, the highest priority of all; `COLT` bit 32; `NT_ONUISTMT 0x8F`); only events queued after `ON UI` count. **The handler fetches the events itself**: `E=UI("EVENT")` in a loop until it is 0, then `RETURN`; the handler is entered once per *new* event (the host's counter `UI("EVENTS")`, `ui_event_count()`), so a handler that leaves events in the queue is not entered again for the same ones. Events are queued by `UI UPDATE` (the frame loop), nothing else. A run's end switches it off. Example: `10 ON UI GOSUB 200` ... `200 E=UI("EVENT"):WHILE E<>0:...:E=UI("EVENT"):WEND:RETURN`. Window host only (the console host has no UI).

## Canvas (the cells of a picture) and the editors
`UI CANVAS id,x,y,w,h,cw,ch` (2026-11-05): a zoomed grid of `cw` x `ch` cells (1..256 each way), each cell a **palette index** of the graphics layer (0 is drawn as a checkered "transparent"); the cell size is the largest whole number of pixels that fits, the grid is centered, a one pixel gap separates cells of 4 pixels or more. `UI PIXEL id,x,y,c` sets a cell, `UI("PIXEL",id,x,y)` reads one (-1 for a bad id or place), `UI IMAGE id,a$` fills the cells from a string of `cw * ch` bytes (row by row; a short string clears the rest), `UI GETIMAGE id,a$` reads them as such a string, the same form as `SPRITE GET` / `SPRITE DEF` (384 bytes for 16 x 24). Events: **kind 7** when the left button is pressed on a cell or dragged onto another one, **kind 8** for the right button; the value is `y * cw + x`; one event per cell until the buttons are let go. A canvas is no tab stop and takes no keys. It can also be a palette: fill it with the colors and read the clicks.

**The sprite and tile editor** (it imports and exports BMP sheets with the buttons Import BMP / Export BMP, roadmap item 53 follow-up) is a BASIC program on top of that, `tools/spriteed.bas` (a *tool*: `TOOL "spriteed"` runs it without losing the program in memory, roadmap item 70) (roadmap item 7, first version; **undo and redo of 30 steps since 2026-11-05**: a stroke, a transformation or Revert is one step; **groups since 2026-11-05** (roadmap item 62): the slider Size makes the canvas a block of 2, 3, 4, 6 or 8 pictures (1 x 1 up to 4 x 2 and 2 x 4), shown in the preview as a real sprite group (`SPRITE 240,SIZE w,h`, the scratch pictures are the sprite images 248..255, so sprite pictures go to 247), saved as one `DESIGN` listing with a `' GROUP w,h` line and one `DESIGN` block per picture): the 16 x 24 picture on a canvas, the 16 colors of a palette window on another (the layer's palette is copied into the graphics layer's entries 1..223, so the theme colors 224..239 cannot be edited), pen and fill, clear / flip, a preview as a real sprite (the scratch sprite 247 with the image 255, so the editable images are 0..254), `Store` (`SPRITE DEF` / `TILE DEF`) and `Revert` (`SPRITE GET` / `TILE GET`), and `Open...` / `Save...` through the file requester: a picture is saved as a numbered **`DESIGN` listing** (`10 DESIGN SPRITE n,base` and 24 `@ "row"` lines), which `MERGE` / `LOAD` bring into a program, so no new file format was needed. A picture can be saved when its colors fit one window of 15 colors above `base`.

## The library uikit and the music and sound editors
(2026-11-05.) `demos/lib/uikit.lib` (`LOAD LIBRARY "uikit"`, prefix `UK_`) collects the small things a form needs: **modal dialogs** `CALL UK_MSG(title$, text$)` (OK), `FN UK_ASK(title$, text$)` (Yes / No: -1 / 0) and `FN UK_INPUT$(title$, prompt$, default$)` (a line of text; `UK_OK` tells OK from Cancel); a `|` in the text starts a new line. They use the widget ids 940..959, run their own event loop and put everything away again, so **call them from the `ON UI` handler** (as the file requester) **or after `ON UI OFF`**: with the handler armed in the main program it would take the dialog's events away. **Sliders with a label and a readout:** `CALL UK_SLIDER(id,x,y,w,label$,min,max,value)` (ids `id`, `id+1`, `id+2`; `CALL UK_DIVISOR(d)` before it makes the readout show position / d), `FN UK_TRACK(e,v)` for the events (updates the readout, returns -1 for such a slider), `FN UK_VAL(id)`, `CALL UK_SET(id,pos)`, `CALL UK_READ(id,text$)`. `demos/lib/mml.lib` (prefix `MK_`) is a tokenizer for the music strings of `PLAY` / `SFX` (no UI).

**The multi-line text editor** (2026-11-06, roadmap item 67 step 3): `UI EDIT id, x, y, w, h, text$` makes a text area (`UIK_EDIT`) with the fixed 8 x 12 font: the lines are separated by LF (`CHR$(10)`), the text is at most 60000 bytes (`UI_EDITMAX`), `UI CAPTION id, text$` sets it (the caret goes to the start, nothing is selected, the undo is empty) and `UI GETTEXT id, a$` reads it (up to 65535 bytes). **Keys:** characters (typing replaces a selection), Return (a new line as indented as the one it leaves), BackSpace, Delete, the cursor keys (Up / Down keep the column), Home / End, Page up / down, Ctrl+Home / End; **Shift** with a cursor key selects, Ctrl+A selects everything; **Ctrl+C / X / V** copy, cut and paste (also Ctrl+Insert, Shift+Delete, Shift+Insert), **Ctrl+Z / Ctrl+Y** undo and redo (24 steps, typing and deleting in a row is one step). **Ctrl+C is the break key while a program runs** (it stops the program: use Ctrl+Insert there; the editor window `EDIT WINDOW` is not a program and takes Ctrl+C). **Mouse:** a click puts the caret, dragging selects (the view follows below the text), a double click selects the word, a triple click the line, the wheel scrolls, and when there are more lines than rows the widget has a vertical scroll bar like a list. **Tab** is the focus key as everywhere (it does not insert a tab). **Events:** `UIE_CHANGE` with the length of the text after every change. **Queries:** `UI("CARET", id)` (the caret as a byte position from 0), `UI("LINE", id)`, `UI("COLUMN", id)` (from 0), `UI("SELECTED", id)` (the length of the selection), `UI("LINES", id)`; the statement `UI CARET id, pos` moves the caret (and drops the selection). The clipboard is the system's (SDL) in the window and the internal one of `clipboard.h` where there is none (`ui_t.clip_get` / `clip_set`). **Keys with Shift or Ctrl** reach the UI as the key code plus `UIKEY_SHIFT` (0x10000) / `UIKEY_CTRL` (0x20000) (Ctrl + a letter is `UIKEY_CTRL | 'a'..'z'`); every other widget takes Shift + a key as the key and ignores Ctrl + a key, so nothing else changed. To get Ctrl + a letter at all, **the window now delivers Ctrl + a letter to `INKEY$` / `GET` as the control code 1..26** (except Ctrl+C, the break key, while a program runs): `INKEY$` returns `CHR$(22)` for Ctrl+V. Design decisions I took (revisit if unwanted): fixed font only, no word wrap, no tabs, Tab is the focus key, 24 undo steps as whole-text snapshots, the text limit 60000. `demos/notepad.bas` is a small text editor built on it. Tests: `uitest1` 261 (the editor with a fake clipboard: typing, selection, clipboard, undo, mouse, scrolling, limits).

**The editor window `EDIT WINDOW`** (step 4): the statement `EDIT WINDOW` (or `ENGINE1999_EDITOR=window` in the environment, which makes plain `EDIT` do it) opens the stored program as text in that widget on the graphics layer of the window version: a panel "Program editor" over the whole screen with the editor and the buttons **OK** (enter the text as the program and close), **Apply** (enter it and stay), **Cancel** (close without); ESC closes when nothing changed, with changes the first ESC only warns and the second discards. Entering the text means `NEW` and every line entered like a typed one (`repl_apply_text()` in `basrepl.c`): every non-blank line must start with a line number (else nothing is changed and the message names the text line), a line number alone is ignored, lines the compiler refuses are dropped and counted in the message; the name of the file stays. It is the same editor as `UI EDIT`, so selection, the clipboard and undo work as above. The console version has no widgets: there `EDIT WINDOW` and the setting open the text editor like `EDIT` (the full-screen editor of the text screen, which has selection and the clipboard, too: `docs/display-engine.md`). The window version's default stays the text screen editor (my recommendation, see roadmap item 67): it has what a BASIC editor needs (line numbers, automatic numbers, syntax colors) and is the same in both hosts.

**The font editor `tools/fonted.bas`** (2026-11-06, roadmap item 72) edits the text screen font through `SYMBOL` and the new queries `TXT("GLYPH",code,row)` / `TXT("BUILTIN",code,row)` (one row byte, bit 7 = left; the built-in font is never changed): a 16 x 16 table at real size (a canvas of 128 x 192 cells, scale 1; the canvas must be a little larger than its cells), an 8 x 12 grid, undo of 30 steps, Save / Open as `DESIGN CHAR` listings. It changes palette entries 1, 2, 4, 5 of layer 3 and puts them back. Two editors are built on them: **`tools/musiced.bas`**, a music editor (voices as lists of tokens, a piano of twelve buttons, length / dot / octave / tempo / volume / wave / style controls, edit / delete / insert behind the selection, Play, Save / Open, Export as a `PLAY` line) and **`demos/sfxed.bas`**, a sound effect editor (sliders for the pitch sweep, length, volume, envelope, vibrato and tremolo, presets and Random, the string in a text field that can be edited and applied, Save / Open / Export as `SFX n,"..."` lines). `demos/spriteed.bas` uses `UK_ASK` (quit with an unstored picture) and `UK_MSG` (errors). Things the work showed: a BASIC procedure takes at most 8 arguments; `BUILD`, `OCT` and similar are reserved words; **the bold UI font drew `#` as a block** (the double strike filled the gap between its bars: fixed in `font.c`, `#` is not smeared).

**The instrument editor `tools/insted.bas`** (2026-11-10, roadmap item 85) edits the definition string of a synthesizer instrument (`docs/sound.md` "Instruments"): six tabs (a `UI TAB` strip; Osc 1 to 3 with FM index and Mod, Filter, Env, FM = FM decay and Poly voices) on one 640 x 300 form, the values kept in BASIC arrays (the model, in slider units) so that the string code (`PARSE` / `MAKE$`) runs without a window (`INSTED_HEADLESS=1`, `instedtest.sh`), the 16 factory instruments as definition strings in `DATA` lines (`synthtest1` compares them with `synth.c`). **The UI held at most 128 widgets (`UI_MAXWIDGETS`, 192 since 2026-11-11 when the FM controls were added)**: the three oscillators share one set of controls (the tabs reload them from the model), pages are shown and hidden with `UI SHOW` over the ids each page registered (`UI SHOW` of an unknown id is an error). **Hold** keeps the note sounding (`SOUND 1,f,-1,v`) and every control change redefines the instrument (`INSTRUMENT 31,a$`: the channel using it gets a new snapshot at once), so a slider is heard while it moves. Found while building it: an error inside an `ON UI` handler followed by `RESUME label` used to leave the handler's slot busy for good (all UI events dead afterwards; also in the other editors): fixed in the VM (`RESUME label` leaves running handlers, `docs/basic-language.md` "RESUME").

## Scroll bars
A scroll bar has an arrow button at each end, a light / gray checkered track and a raised knob whose length is `page / (range + page)` of the track (at least 10 pixels), with a grip. A click on an arrow moves one step, a click in the track one page; both repeat while the button is held (after 400 ms, then every 60 ms; the track repeat stops when the knob reaches the mouse); the knob can be dragged; the wheel moves 3 steps; with the focus the arrow keys, Page up / down, Home and End work. A **list** that has more rows than it shows gets such a bar by itself (it only scrolls the view: the selection does not change).

## The end of a run
The UI belongs to the program that opened it: when a run stops (END, an error, Break) the host closes the UI and clears the graphics layer, so that the prompt is visible again. (Before this was done, ESC, which is the break key, left the form over the text screen and it looked like a hang.) A program that wants ESC for itself (cancel a dialog) uses `BREAK OFF`; Ctrl+C still stops it.

## The file requester
A library, `demos/lib/filereq.lib` (`LOAD LIBRARY "filereq"`, prefix `FR_`; demo `demos/filedlg.bas`), written in BASIC on top of the widgets, as the plan said. `F$=FN FR_PICK$(title$, dir$, pattern$, save)` opens a **modal** dialog on the open UI (so `UI OPEN` first) and returns the full name the user chose or `""` for Cancel / ESC. The dialog shows the full name of the directory, a list (`../` first, then the sub-directories with a `/`, then the files that match `pattern$`: `"*.bas;*.lib"`, `""` = all; hidden names are not shown), a name field, OK and Cancel. A double click (or Return) on a directory enters it, a click on a file puts its name into the field, a double click on a file, OK or Return in the field accepts; an empty field takes the highlighted row. With `save` = -1 an existing file asks "Replace?" (Replace / Keep); with 0 the user picks. `FR_DIR$` holds the directory the dialog ended in: pass it as `dir$` the next time. The library uses the widget ids 900..913 and the channel 255 (closed again); the widgets are removed when it returns and the form behind it is redrawn. A directory with more than 500 entries shows the first 500. The names come from the **`dir:` driver** (`OPEN "dir:/path/*.bas" FOR INPUT AS #1`, see `io-subsystem.md`). The file name is *returned*, never opened by the requester, so the program decides (and the sandbox of a later security policy applies as usual).

## Windows (overlapping, draggable)
`UI WINDOW id,x,y,w,h,title$` (2026-11-05) is a panel that behaves like a window: **drag it by its title bar**, **click anywhere in it to bring it to the front**, and the small box at the right of the title bar asks to **close** it (the event kind 6, cancel, with the window's id: the program decides, usually it removes the window). The title bar of the window in front is blue, the others gray. Windows overlap freely; z order is the order in the widget list, which `ui_raise()` changes (a raised window and its widgets go to the end). **Ownership:** a widget created inside a window's rectangle belongs to the topmost window that contains it (`owner`), and moves and rises with it, so create the widgets right after their window. `UI MOVE id,x,y` moves a window (with its widgets) or a plain widget, `UI RAISE id` brings a window to the front. To close a window, `UI REMOVE` its widgets first, then the window (removing a window does not remove its widgets). A window cannot be dragged out of the screen (40 pixels of its width and the title bar stay). **Damage lists** (2026-11-05): every widget has a damage list (`ui_dmg_t`, up to 8 rectangles, merged into their bounding box beyond that): the parts of its rectangle that are not valid on the canvas (never drawn, overwritten by a widget in front, changed while hidden by one). `ui_draw()` goes through the widgets from the back to the front and draws only *damage ∩ visible part*, where the visible part is the widget's rectangle minus the rectangles of the visible widgets in front of it that belong to another group (a window and the widgets it owns, or a plain panel and the widgets that lie inside it, form one group and do not hide each other). The rest stays on the list: **a window that another window covers gets the covered area on its list** (when the other one is added, raised, moved or shown), is not drawn there (so a change in the hidden part never shows through the window in front), and **when the area is revealed** (the window in front moves, closes, hides) **it is drawn then**; a place that a moved, hidden or removed widget leaves goes to the desk (a desk damage list, filled with the desk color where no widget is) and to every widget under it. A widget that was drawn over something in its own group puts that on the lists of the widgets in front of it in the group, which are drawn right after. A redraw that would need more than 96 rectangles falls back to a full draw. `uitest1` compares the incremental redraw with a full redraw after 400 random steps of moving, raising, hiding, changing and removing windows. A plain `UI PANEL` stays what it was (a fixed panel; `UI MODAL` works with both). Demo: `demos/windows.bas`. Tab order follows the widget list, so it changes when windows are raised.

## Game controllers and the focus
(2026-11-05.) While the UI is open, the game controllers drive it like a keyboard (`ui_pad_keys()`, fed by the host at every `UI UPDATE`, any plugged-in pad): **D-pad or left stick** = the arrow keys (they repeat while held: 400 ms, then every 60 ms), **A** presses (Space; Return in a list or a text field), **Start** = Return, **B** = Escape (closes a pop-up or cancels a modal dialog), **LB / RB** = Shift+Tab / Tab. The buttons are read as *state* (`joy_buttons()`), so the latches of `JOY("PRESSED")` are not touched and a program can read the pad as well. **`UI JOY 0`** switches this off (a game that uses the pads for itself while a UI is open), `UI JOY 1` on again; every `UI OPEN` starts with it on.
An **arrow key that the focused widget does not use moves the focus to the nearest widget in that direction** (buttons and check boxes: all four; text fields: up / down; lists: left / right; the nearest by distance along the direction plus twice the offset across it), so a form can be crossed with the D-pad, and the keyboard arrows do the same. Sliders, scroll bars and radio groups keep all arrows for themselves: leave them with LB / RB (Tab) or the mouse.

## Keys
Tab / Shift+Tab move the focus; Space and Return press buttons and toggle boxes; arrows work in lists (Home, End, Page up / down), sliders and radio groups; text fields take typing, Backspace, Delete, Home, End, Left, Right.

**Caret:** the editor's caret is a **blinking block** one character wide with the character under it inverted (500 ms on, 500 ms off; solid for 500 ms after every key or mouse action), like the text screen editor's; text fields (proportional font) keep the thin line (roadmap item 69).

## Colors, themes and syntax highlighting (roadmap item 68, 2026-11-06)
**Per widget:** `UI COLOR id, fg [, bg]` sets the text color and the background of one widget (a palette entry 1..255 of the UI's layer; **-1 = the theme's color**; a missing `bg` stays as it is). The text color is the caption of a label, button, check box and radio button, the text of a text field, list and editor (and the editor's caret); the background is the face of a button and panel, the field of a text field, list and editor, and a fill behind a label, check box and radio button (they have none by default). A disabled widget keeps the theme's disabled color. `UI("COLOR", id, 0|1)` reads the text / background color (-1 = the theme's). **Entry 0 is refused** ("Illegal argument"): it is transparent in every layer (a widget painted with it would show the layers behind it, and it is the background of the mouse pointer's pictures), and so is anything outside 1..255.
**Themes:** `UI THEME n` loads a preset into the palette entries 224..239 (the widgets: `UI_PAL_COLORS`) and 240..255 (the syntax colors: `UI_SYN_COLORS`) of the graphics layer and redraws: 0 classic grey (what `UI OPEN` sets), 1 dark, 2 high contrast; `UI("THEME")` is the number set last. A program may still set any entry itself with `GFX PALETTE 3, 224 + i, argb`. Only the UI's layer (3) is written, never the sprite layer (4) that colors the mouse pointer. **The entries 240..255 belong to the UI now** (they were free before; the demos do not use them next to a UI). `ENGINE1999_UITHEME=0|1|2|classic|dark|contrast` chooses the theme of the editor window `EDIT WINDOW` (default classic).
**Syntax highlighting in `UI EDIT`:** `UI SYNTAX id, 1` colors the text as BASIC source with the colors of `LIST` (line number, statement, control flow, command, function, operator, identifier, number, string, shell literal, comment, punctuation); `UI SYNTAX id, 0` is plain text again; `UI("SYNTAX", id)` reads the mode (-1 for a bad id). The lexer is `synhl.[ch]` (no UI, no VM): it uses the tokenizer's own scanners and `keyword_hlclass()`, so it agrees with `LIST` and the text screen editor (`synhltest1` compares every line of the demos with `detokenize_line_hl()`); a line is lexed on its own (BASIC has no multi-line strings or comments) and only the visible rows are. `UI SYNTAXCOLOR slot, c` chooses the palette entry a slot 0..15 is drawn with (the default is 240 + slot; slot 0 = plain text uses the widget's text color; the slots are the `hlclass_t` numbers: 1 line number, 2 statement, 3 control, 4 command, 5 function, 6 operator, 7 identifier, 8 number, 9 string, 10 shell, 11 comment, 12 punctuation, 13..15 free); `UI("SYNTAXCOLOR", slot)` reads it. **For other languages the program gives the classes:** `UI HILITE id, a$` takes one byte per byte of the text (the low four bits are the slot; LF counts), switches the editor to mode 2 and keeps the classes while the text is edited: they move with the text (what is typed is plain until the program colors it again, which it does on the change event `UIE_CHANGE`); a new text (`UI CAPTION`) clears them. The VM is slow for big texts, which is why BASIC is built in. A disabled editor is drawn in plain colors. `EDIT WINDOW` turns the BASIC mode on; `demos/notepad.bas` has buttons for the mode and the theme.
Decisions I took (revisit if unwanted): colors are palette indices, not RGB; one color per widget (no colored runs in labels / text fields); the classic theme stays the default of everything; the text screen editor keeps the `LIST` highlighter (it works on the tokenized program); `LIST` now colors `<=`, `>=`, `<>` and `&` as operators (they had the statement color: a bug found by `synhltest1`). Tests: `uitest1` 297, `synhltest1` (spot checks and every line of the demos and libraries), `vmtest1` 1388.
