# The UI subsystem

Widgets (panels, labels, buttons, check boxes, radio buttons, text fields, lists, sliders, progress bars) drawn on the **graphics layer** (layer 3, 640 x 300), driven by the mouse and the keyboard. Roadmap item 47 / section 15. Demo: `demos/ui.bas`. Window host only: the console host answers "Not available in the console host" (a text screen renderer is a later step).

## Layers of the implementation
- `font.[ch]` (no SDL): proportional fonts built from the 8 x 12 font (sans = ink columns shifted left plus one pixel gap, bold = double strike). `font_measure()`, `font_draw()`, `font_fit()`. Test: `fonttest1`.
- `ui.[ch]` (no SDL, no VM): the retained widget table (up to 128 widgets, ids chosen by the caller), theme, drawing of the changed parts only, hit testing, focus / Tab order, text editing, lists, sliders, modal panel, pop-up, an event queue of 64. It draws through a small canvas table (`ui_canvas_t`: box and pixel), so it is tested on a `gfxcore` bitmap. Test: `uitest1` (122 checks, pixel checks included).
- `gfxops.c` rows (group `UI`) and the extension word `UI` (`XF_UI`) in the parser; the host (`engine1999.c`, `host_ui_op()`) maps them to `ui.h`; the mouse comes from `mouse_get()` and the keys from `sdlscr_pollkey()` (escape sequences parsed with `keyseq_parse()`).

## Decisions taken (owner, 2026-11-01) and mine
- The UI owns the graphics layer; its theme uses the palette entries 224..239 of that layer (`UI_PALBASE`); the mouse pointer sprite stays in front; `UI OPEN` shows the pointer permanently.
- One form plus modal panels and pop-ups first; overlapping windows later. Retained widgets.
- Mine: widgets are drawn in creation order (z-order = order of creation); a **pop-up is a hidden list** that `UI POPUP id,x,y` shows (a click outside or Escape closes it with a cancel event); a **modal panel** (`UI MODAL id`) makes only the panel and widgets lying inside it react; events are polled with `UI("EVENT")` or delivered to a handler by `ON UI` (below).

## Statements
`UI OPEN`, `UI CLOSE`, `UI CLEAR`, `UI UPDATE`; `UI LABEL|BUTTON|CHECK|TEXT|PANEL id,x,y,w,h,text$`; `UI RADIO id,x,y,w,h,text$[,group]`; `UI LIST|PROGRESS id,x,y,w,h`; `UI SLIDER id,x,y,w,h[,min]`; `UI SCROLL id,x,y,w,h[,page]` (a scroll bar: vertical when it is higher than wide; positions 0..100 until `UI RANGE id,min,max`; `UI PAGE id,n` sets the size of the visible part, which sizes the knob and the Page up / down step; events: change with the position); `UI REMOVE|FOCUS|CLEARLIST|MODAL id` (`MODAL 0` ends it); `UI CAPTION|ITEM id,text$`; `UI VALUE|ENABLE|SHOW id,n`; `UI RANGE id,min,max`; `UI POPUP id,x,y`; `UI GETTEXT id,a$`; `UI ITEMTEXT id,row,a$`.

## Functions
`UI("EVENT")` next event id (0 none; makes it current), `UI("KIND")`, `UI("VALUE")` of the current event, `UI("GET",id)`, `UI("COUNT",id)` rows of a list, `UI("FOCUS")`, `UI("OPEN")`, `UI("EVENTS")` (the number of events queued so far; what `ON UI` watches), `UI("PIXEL",id,x,y)`.
Event kinds: 1 click (button), 2 change (check, radio, slider, text field: the new length), 3 select (list row), 4 double click (or Return in a list), 5 Return in a text field, 6 cancel (Escape in a modal panel / pop-up, click outside a pop-up), 7 / 8 a canvas cell with the left / right button.

## ON UI
`ON UI GOSUB|GOTO target` / `ON UI OFF` (2026-11-05): a handler that runs between two statements whenever a widget has queued an event, so the main loop only has to call `UI UPDATE`. An event slot like `ON MOUSE` / `ON KEY` (`VM_UISLOT` 8, the highest priority of all; `COLT` bit 32; `NT_ONUISTMT 0x8F`); only events queued after `ON UI` count. **The handler fetches the events itself**: `E=UI("EVENT")` in a loop until it is 0, then `RETURN`; the handler is entered once per *new* event (the host's counter `UI("EVENTS")`, `ui_event_count()`), so a handler that leaves events in the queue is not entered again for the same ones. Events are queued by `UI UPDATE` (the frame loop), nothing else. A run's end switches it off. Example: `10 ON UI GOSUB 200` ... `200 E=UI("EVENT"):WHILE E<>0:...:E=UI("EVENT"):WEND:RETURN`. Window host only (the console host has no UI).

## Canvas (the cells of a picture) and the editors
`UI CANVAS id,x,y,w,h,cw,ch` (2026-11-05): a zoomed grid of `cw` x `ch` cells (1..256 each way), each cell a **palette index** of the graphics layer (0 is drawn as a checkered "transparent"); the cell size is the largest whole number of pixels that fits, the grid is centered, a one pixel gap separates cells of 4 pixels or more. `UI PIXEL id,x,y,c` sets a cell, `UI("PIXEL",id,x,y)` reads one (-1 for a bad id or place), `UI IMAGE id,a$` fills the cells from a string of `cw * ch` bytes (row by row; a short string clears the rest), `UI GETIMAGE id,a$` reads them as such a string, the same form as `SPRITE GET` / `SPRITE DEF` (384 bytes for 16 x 24). Events: **kind 7** when the left button is pressed on a cell or dragged onto another one, **kind 8** for the right button; the value is `y * cw + x`; one event per cell until the buttons are let go. A canvas is no tab stop and takes no keys. It can also be a palette: fill it with the colors and read the clicks.

**The sprite and tile editor** is a BASIC program on top of that, `demos/spriteed.bas` (roadmap item 7, first version): the 16 x 24 picture on a canvas, the 16 colors of a palette window on another (the layer's palette is copied into the graphics layer's entries 1..223, so the theme colors 224..239 cannot be edited), pen and fill, clear / flip, a preview as a real sprite (the scratch sprite 247 with the image 255, so the editable images are 0..254), `Store` (`SPRITE DEF` / `TILE DEF`) and `Revert` (`SPRITE GET` / `TILE GET`), and `Open...` / `Save...` through the file requester: a picture is saved as a numbered **`DESIGN` listing** (`10 DESIGN SPRITE n,base` and 24 `@ "row"` lines), which `MERGE` / `LOAD` bring into a program, so no new file format was needed. A picture can be saved when its colors fit one window of 15 colors above `base`.

## Scroll bars
A scroll bar has an arrow button at each end, a light / gray checkered track and a raised knob whose length is `page / (range + page)` of the track (at least 10 pixels), with a grip. A click on an arrow moves one step, a click in the track one page; both repeat while the button is held (after 400 ms, then every 60 ms; the track repeat stops when the knob reaches the mouse); the knob can be dragged; the wheel moves 3 steps; with the focus the arrow keys, Page up / down, Home and End work. A **list** that has more rows than it shows gets such a bar by itself (it only scrolls the view: the selection does not change).

## The end of a run
The UI belongs to the program that opened it: when a run stops (END, an error, Break) the host closes the UI and clears the graphics layer, so that the prompt is visible again. (Before this was done, ESC, which is the break key, left the form over the text screen and it looked like a hang.) A program that wants ESC for itself (cancel a dialog) uses `BREAK OFF`; Ctrl+C still stops it.

## The file requester
A library, `demos/lib/filereq.lib` (`LOAD LIBRARY "filereq"`, prefix `FR_`; demo `demos/filedlg.bas`), written in BASIC on top of the widgets, as the plan said. `F$=FN FR_PICK$(title$, dir$, pattern$, save)` opens a **modal** dialog on the open UI (so `UI OPEN` first) and returns the full name the user chose or `""` for Cancel / ESC. The dialog shows the full name of the directory, a list (`../` first, then the sub-directories with a `/`, then the files that match `pattern$`: `"*.bas;*.lib"`, `""` = all; hidden names are not shown), a name field, OK and Cancel. A double click (or Return) on a directory enters it, a click on a file puts its name into the field, a double click on a file, OK or Return in the field accepts; an empty field takes the highlighted row. With `save` = -1 an existing file asks "Replace?" (Replace / Keep); with 0 the user picks. `FR_DIR$` holds the directory the dialog ended in: pass it as `dir$` the next time. The library uses the widget ids 900..913 and the channel 255 (closed again); the widgets are removed when it returns and the form behind it is redrawn. A directory with more than 500 entries shows the first 500. The names come from the **`dir:` driver** (`OPEN "dir:/path/*.bas" FOR INPUT AS #1`, see `io-subsystem.md`). The file name is *returned*, never opened by the requester, so the program decides (and the sandbox of a later security policy applies as usual).

## Game controllers and the focus
(2026-11-05.) While the UI is open, the game controllers drive it like a keyboard (`ui_pad_keys()`, fed by the host at every `UI UPDATE`, any plugged-in pad): **D-pad or left stick** = the arrow keys (they repeat while held: 400 ms, then every 60 ms), **A** presses (Space; Return in a list or a text field), **Start** = Return, **B** = Escape (closes a pop-up or cancels a modal dialog), **LB / RB** = Shift+Tab / Tab. The buttons are read as *state* (`joy_buttons()`), so the latches of `JOY("PRESSED")` are not touched and a program can read the pad as well. **`UI JOY 0`** switches this off (a game that uses the pads for itself while a UI is open), `UI JOY 1` on again; every `UI OPEN` starts with it on.
An **arrow key that the focused widget does not use moves the focus to the nearest widget in that direction** (buttons and check boxes: all four; text fields: up / down; lists: left / right; the nearest by distance along the direction plus twice the offset across it), so a form can be crossed with the D-pad, and the keyboard arrows do the same. Sliders, scroll bars and radio groups keep all arrows for themselves: leave them with LB / RB (Tab) or the mouse.

## Keys
Tab / Shift+Tab move the focus; Space and Return press buttons and toggle boxes; arrows work in lists (Home, End, Page up / down), sliders and radio groups; text fields take typing, Backspace, Delete, Home, End, Left, Right.

## Not done
overlapping and draggable windows, combo boxes, the console text renderer, a tile map editor and animations in the editors. Widgets are not drawn until `UI UPDATE` runs (the demo updates once per frame).
