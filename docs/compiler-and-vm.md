# Program store, compiler, code generator, VM

## Program memory (`baslin.[ch]`, `baspgm.[ch]`)

`program_t` = `first`/`last` pointers of a doubly linked list of heap-allocated `line_t` nodes (`next`, `prev`, `lineno`, `toklen`, flexible `tokens[]`), sorted by line number. `init_program`/`free_program` manage it; `find_line`, `create_line`, `link_line`, `unlink_line`, `delete_line` and `enter_line` (insert/replace/delete) operate on it. `pgmiter_t` walks the list and exposes the current line as `tok` + `hdr`.
`linehdr_t{lineno, length}` is only the *encoded* header of a tokenized line (`LINEHDR_SIZE` = 5 bytes: `lineno.24 length.16`, big endian), produced by `tokenize_line` and consumed by `enter_line`; it is not stored in the program.

Key operations: `init_program`, `find_line` (returns `FOUND_EXACT/INSERT/BEYOND/NONE/ERROR` with neighbours), `create_line`, `emplace_line`, `update_line`, `unlink_line`, `quick_append_line`,
`defrag_memory`, `enter_line` (the user-facing entry; empty line body deletes, no number → direct-mode callback), iteration via `pgmiter_t` (`begin_iterate_program`/`step_iterate_program`), and `list_program`.

## Syntax tree (`bascomp.[ch]`, `nodetype.[ch]`)

`compiler_t` holds token cursor state (`iter`, `tokp`, `tokend`, `currtok`, heap `param`, `number`; set the token range with `comp_set_tokens()`, release with `cleanup_compiler()`), a context stack for backtracking (`comp_push_context` / `comp_commit_context` / `comp_pop_context`) and the syntax tree (`syntree` root; `nodes` chains every allocated node).

`node_t` = `{ chain, branches (growable array of node_t*), numbranches, maxbranches, datalen.16, type.8, data[] }`, one heap allocation per node (branch array separate). Branch count is unlimited; a branch may be `NODE_NONE`, standing for an optional branch that is absent. `chain` links all nodes of a compiler so abandoned parses are freed too (`comp_free_tree`, called by `cleanup_compiler`).
Create with `comp_create_node(comp, &node, type, nbranches, datalen, data, branch…)` (variable arguments are `node_t*`), append branches with `comp_add_branch`, iterate with `comp_node_iter_branches`; consumers read `node->type`, `node->data`, `node->datalen`, `node->branches[i]`.
Generic list parsing helpers: `comp_eat_list` / `comp_eat_list2` (separator tokens, operator-precedence flavour).

`comp_eat_*( comp, node_t** pnode )` return `false` on hard failure; a successful call may leave `*pnode == NODE_NONE` meaning "this rule did not match" (callers test both).
`comp_error` reports and halts. `run_compiler` is the driver; `begin_comp` primes the first token.

Node types (`NT_*`, documented per type in `nodetype.h` including the *immediate processing* each does): expression lists, array subscripts/declarations, variable refs (base vs full),
literals, user/system function names and calls, the expression-level nodes (`NT_STRADDEXPR`, `NT_NUMUNARYEX … NT_NUMOREX`, `NT_NUMCMPEX`), statements (`NT_PRINTSTMT`, `NT_LETSTMT`, `NT_DIMSTMT`, `NT_FORSTMT`, `NT_GOTOSTMT`, …) and containers (`NT_STMTLIST/LINE/LINES`).
`nodename()` gives printable names for debugging.

## Variable memory (`vars.[ch]`)

Every variable is its own heap allocation (`var_t`: type, name, value or array elements or function parameter list), found through a growable table of pointers by its **variable number** (`uint16_t`, `VAROFFS_NONE` = 0xFFFF reserved, so at most 65535 variables; numbers of deleted variables are reused) and through a hash table by (type, name). The variable number is what the syntax tree and the instructions (`RRNV`, `WRNV`, `CALF`, …) carry, so they stay valid while the variable exists. Strings, names and arrays are heap allocated; there are no fixed areas, no compaction, and no limit on names, strings (the VM still limits them to 65535 bytes) or the number of array elements other than `MAXELEMS` and available memory. One array dimension is still a 16-bit value (≤ 65535), at most `MAXDIM` = 6 dimensions, `MAXPARAM` = 8 function parameters.

Type byte: bit 5 = user function, bit 4 = array, low bits = element type (`0` float64, `1` int16, `2` string = pointer + length, `3` label = 32-bit code offset). A and A% and A$ are three variables; so are A and A(…). New variables are zero / the empty string / `CODEOFFS_NONE` (labels and functions).

API: `init_varmem` / `cleanup_varmem` (frees every variable), `vmem_var( vmem, number )` (the `var_t*`), `vmem_create_var / lookup_var / delete_var / get_var / set_var`, `vmem_get_func_info / get_func_param`. `vmem_lookup_var` returns true with `VAROFFS_NONE` when the variable doesn't exist. `vmem_get_var` of a string returns a pointer into the variable (valid until it is modified), `vmem_set_var` copies the string. Arrays are indexed row-major with one index per dimension, each `0 .. dim-1`. Errors (`Variable already exists`, `Array too large`, `Too many variables`, `Out of memory`) go through the `report` / `halt` callbacks. `testcomp1.c` is a randomized stress test of this subsystem (create / delete / read / write against a shadow model).

## Code generator (`codegen.[ch]`)

`codegen_t`: `code`, `data` (heap buffers), sizes, callbacks. Low level: `cgen_alloc_code/data`, `cgen_gen_ins` (4-bit basic instr + optional extension + 16-bit or, if wide, 32-bit param; a parameter above 65535 makes an instruction wide by itself, `cgen_gen_ins12_wide()` forces it, `cgen_patch_param()` patches a wide parameter later), `cgen_gen_ins12`,
`cgen_gen_ins12_imm17`, `cgen_gen_ins4_imm17`. One `cgen_gen_<mnemonic>` wrapper per instruction. Tree walkers `cgen_from_<rule>` mirror the parser rules.

## Instruction set (`instset.h`, the spec)

Stack VM, **two stacks**: data stack of 64-bit doubles (strings are heap pointers that instructions free), return stack of 32-bit code addresses. Forth-style stack comments in the spec.

Encoding: `<ins> [<ext>] [<hi><lo>]`, or `[<b3><b2><b1><b0>]` with the W flag. Instruction byte = `P C E W | iiii` (P: has a param, C: param/stack is code vs data, E: extended 12-bit opcode follows, W: the param has 32 bits). The code generator emits code addresses (`PHPA.C`, `BRIA`, `BRIR`, and `RSTR` with a target) always wide, because they are patched after the instruction was generated (`cgen_patch_param()`); data offsets (`PHPA.D`, `INPL`), `LINE` numbers and `PHIM` immediates only when they don't fit 16 (17) bits. Nothing in a program limits the size of the code or data segment except the soft limit.
Basic opcodes: `BRK NOP PHPA PHIM BRIA BRIR JPCC JUMP DROP LINE LAN LIAN LUAN LAS FRES` (15 = reserved).
Extended: arithmetic/logic (`NEG NOT LSH RSH ADD SUB MUL DIV AND NAND OR NOR XOR XNOR POW`), `CON` (string concat), numeric/string compares (`CNEQ…CSLT`),
variable access (`RRNV RRIV RRSV RRLV RNAE RIAE RSAE`, `WR*`/`W*AE`), calls (`CALF RETF`), and BASIC runtime primitives (`TI INKY ASC VAL FRE LEN BINS … MIDS SLFT SRGT SMID SAVE PCHN PNUM PSTR`). See `instset.h` for the full table and bit layouts.
Immediates: 17-bit signed (`PHIM`, C bit = bit 16) so small integers need no data segment: number literals that are integers from -2147483648 to 2147483647 (not negative zero) are generated as `PHIM` (3 bytes up to ±65535/65536, else wide: 5 bytes) (`cgen_push_number()`), others as a constant in the data segment (`PHPA.D`, `LAN`). The code and data segments are heap buffers that grow on demand (`cgen_alloc_code/data`, soft limit 256 MiB each); identical read-only constants (number literals, string literals, SAVE options, INPUT prompts, the empty string, the `PCHN` channel number, label names and line numbers of LOAD/RUN/LIST/DELETE/RENUM) are stored once (`cgen_data_const()`, a hash table that is cleared with the segment). DATA item records are not shared (they are chained and carry state).

## VM (`vm.[ch]`)

Minimal executor: `init_vm( vm, &codegen, &varmem )`, `vm_run( vm )` (runs from offset 0 to the end of the code, returns `false` after reporting an error), `cleanup_vm`. Stacks are heap arrays that grow on demand; data stack items are tagged number/string (heap, NUL-terminated), so type mismatches are run time errors and strings are freed on errors. Output goes through `vm->print( vm, userdata, channel, text )` (default stdout), errors through `vm->report` (default stderr). `vm->maxsteps` guards against endless loops.

Implemented: control (`NOP PHPA PHIM BRIA BRIR JPCC JUMP DROP LINE`), loads (`LAN LIAN LUAN LAS FRES`), all arithmetic/logical/compare/concat instructions, scalar variable read/write (`RRNV RRIV RRSV RRLV WRNV WRIV WRSV`), array element access (`RNAE RIAE RSAE WNAE WIAE WSAE`: subscripts must be in range, else "Subscript out of range"), user function calls (`CALF RETF`), `PCHN PNUM PSTR`. System functions: `TI INKY FRE ASC LEN VAL STRS CHRS BINS QUAS OCTS HEXS DECS LFTS RGTS MIDS` (details and edge cases in the comment of `vm.h`; `INKEY$` reads from the `vm->inkey` callback, `TI` counts 1/60 s ticks since the VM was created). `SHEX` (a backtick shell literal) runs the command with `popen()` and returns its standard output without the trailing newlines, like a shell command substitution (exit status ignored; more than 65535 bytes of output is an error). `SAVE` ( mode name -- ) can't be done by the VM alone, because the program belongs to the host: after checking the mode (`""`/`B` binary, `A` ascii) the VM calls `vm->save( vm, userdata, filename, ascii )`; without that callback `SAVE` is an error. `baspgm.c` provides `save_program( pgm, FILE*, ascii )` for the host: ascii is the listing (one line per program line), binary is a 5-byte header (magic `89 45 39 39` = 0x89 "E99", then the format version, `PGMFILE_VERSION` = 1) followed by the encoded lines (`linehdr_t` of `LINEHDR_SIZE` bytes + tokens). The first magic byte is not ASCII, so a text listing can't be mistaken for a binary file. `read_program_header( FILE*, &version )` is what a loader calls first: it consumes the header, or rewinds the stream if there is no magic (then it is a text file); there is no loader yet. `RDNM RDST RSTR` implement DATA/READ/RESTORE (below). `INPL INPN INPS INPE GETK` implement INPUT and GET (below). Not implemented (reported as "Instruction XXX not implemented"): `WRLV`, `BRK` (reports "Breakpoint"). `ERAS` (param = variable number) resets an array to its initial state (0 / empty strings). `SLFT SRGT SMID` (substring assignment) take the target string variable as parameter and the subscripts of an array element from the stack, `( s n inx … ndim -- )`, `ndim` = 0 for a plain variable; exact semantics in `instset.h`.

Optional arguments: the parser supplies a literal `-1` for an omitted second argument of `BIN$ QUA$ OCT$ HEX$ DEC$` (digits) and an omitted third argument of `MID$` (length), so the instructions always get all their arguments; `cgen_from_expr` accepts such a bare `NT_NUMLIT`.

`CALF` pops the argument count and the arguments, saves the current values of the parameter variables (strings as heap copies) in a context kept by the VM (`vm_context_t`, indexed by a 16-bit number), assigns the arguments to the parameter variables, pushes `<return address> <context index>` on the return stack and branches to the function. `RETF` restores the variables and returns; the result stays on the data stack. `vm_run_at( vm, start )` runs from a given code offset (needed when direct mode lines are appended to the code).

Policies the ISA leaves open (documented in `vm.h`): comparisons give -1/0; bitwise ops work on 32-bit signed integers; print separator parameter 0 = newline, 4 = `;`, 8 = `,` (next 10-column zone); numbers print with `%.15g`.

Code generator driver: `cgen_from_program( cgen, comp )` handles `NT_STMTLINES` / `NT_STMTLINE` / `NT_STMTLIST` and the statements `LET`, `PRINT`, `SAVE` (`codegen.c`), `LOAD`, `RUN`, `LIST` (`cgenprog.c`) plus the control flow statements below (`cgenctl.c`); every statement of the grammar has code generation now. Substring assignment (`LEFT$/MID$/RIGHT$(var, …) = expr`, `codegen.c`) needs a string variable or string array element as target; `MID$` without a length replaces up to the end. `LINE` is wide for line numbers above 65535. Call `cgen_reset()` before generating into a reused `codegen_t` and `cleanup_codegen()` / `cleanup_runtime()` when done.

### Declarations (`cgendecl.c`)

- **`DIM`** generates nothing: the compiler creates the array when it parses the declaration (constant dimensions; `DIM A(n)` gives subscripts `0..n-1`), and an array used without `DIM` is created with 10 elements. A second `DIM` of the same array is a compile error ("Variable already exists"), so arrays can't be re-dimensioned.
- **`ERASE a(), b()`** generates one `ERAS` per array. It doesn't free the array, it resets all elements to 0 / the empty string: arrays are created when the declaration is parsed and the code refers to them by variable number, so they always exist. (Re-dimensioning an array is not possible.)
- **`DEF FN`**: the single-line body is generated inline, jumped over (`BRIA end  start: <expr>  RETF  end:`); the start offset is stored in the function variable at compile time. The function must be defined *before* the call in the program text (the parser looks it up while parsing the call), and a function can't call itself (it doesn't exist while its body is parsed). The parameter variables are created if needed. Array parameters aren't supported.
- **Multi-line `DEF FN`**: `DEF FN A(X)` (end of line) statement lines `END FN`. The result is what the body last assigned with `FN A = expr` (new statement `NT_FNASSIGNSTMT`, only accepted inside the body of that same function, with a numeric or string expression depending on the function); if the body never assigns it, the result is 0 or the empty string. The result lives in a hidden variable `@FN<name>`; code: `BRIA end  start: <result = 0 / empty>  <statement lines>  <read result>  RETF  end:`. Statements inside a body are normal lines (they appear in the line table; `FOR`/`NEXT`, `IF`, `GOSUB` work).
- **Spelling:** the tokenizer reads `FNA` as one identifier, so a function is written `DEF FN A(X)=…` and called as `FN A(…)` (with a space).

### DATA, READ, RESTORE (`cgendecl.c`)

- **`DATA`** generates no code. Every item is a record in the data segment, `type.8 next.32 payload` (`DATAREC_HEADER` = 5 bytes, `cgen_datarec_next()`) (type 0 = number, 8 bytes big endian; type 1 = NUL-terminated string), and the records are chained in program order through `next`; `codegen_t.datafirst` is the first one (`DATAOFFS_NONE` = none) and `codegen_t.dataoffs` lists all items (compile time only). Items are numeric literals (optionally signed, any base) and string literals; unquoted text isn't supported. The items share the data segment with the literals of the program.
- **`READ v1, v2, …`**: for every variable `RDNM` (number) or `RDST` (string) reads the next item, then the value is stored like in an assignment (plain variables and array elements, numeric, integer and string). The VM keeps the data pointer (`vm_t.datapos`); an item of the wrong type is a type mismatch error, and reading behind the last item is "Out of DATA". `vm_run()` starts a program with the first item (like `RESTORE`); `vm_run_at()` keeps the pointer.
- **`RESTORE`** (`RSTR`) goes back to the first item; **`RESTORE line`** to the first item in that line or the next lines having one, **`RESTORE label`** to the first item behind the label (resolved at the end of code generation, like jumps: tables in `codegen_t` — `restorefix`, `labeldata`, and `dataindex` in the line table). Nothing behind the target means the next `READ` is "Out of DATA".

### Control flow (`cgenctl.c`)

- **Line table and fixups:** every numbered line is recorded (`cgen_note_line`, line number → code offset). `GOTO`/`GOSUB`/`IF … <line>` emit a `BRIA` that is patched by `cgen_finish_control()` when the whole program is known; an unknown target is the compile error "Undefined line number N in line M". Consequence: a line can only jump to lines of the same compilation (direct mode can't `GOTO` a stored program line yet).
- **`GOSUB`/`RETURN`:** `GOSUB` pushes the return address (`PHPA.C`, patched) then branches; `RETURN` is `JUMP`.
- **Labels:** a label is a variable holding a code offset, set at compile time by `LABEL`. `GOTO`/`GOSUB label` do `RRLV` (pushes the offset on the return stack) + `JUMP`; a label that is never defined fails at run time ("Undefined label").
- **`IF`/`UNLESS`:** `<cond> PHPA.C then JPCC <else part> BRIA end then: <then part> end:`; used for the single-line forms (`THEN <line>`, `GOTO`/`GOSUB <line|label>`, `THEN <stmt-list> [ELSE <stmt-list>]`) and the multi-line form. `UNLESS` compares the condition with 0.
- **`FOR`/`NEXT`:** matched at compile time (lexically): `NEXT` closes the innermost open `FOR`, which must use the named variable (`NEXT` alone, `NEXT I` and `NEXT J,I` are accepted; mismatches are "NEXT without FOR" / "FOR without NEXT"). Limit and step live in hidden variables `@FOR<n>L` / `@FOR<n>S`; the loop test happens *before* the first pass (a loop with `FROM` past `TO` runs zero times). The loop variable may be numeric or integer.
- **Loops (`FOR`, `REPEAT`, `WHILE`, `UNTIL`)** share one compile-time stack of open loops (innermost last); the statements are matched by the code generator, not by the parser. `WHILE cond … WEND` runs while the condition is true (test before each pass), `UNTIL cond … UEND` runs until it becomes true (test before each pass), `REPEAT … UNTIL cond` tests after each pass and repeats until the condition is true. Because `UNTIL` is both the end of a `REPEAT` and the start of an `UNTIL … UEND` loop, the rule is: **an `UNTIL` closes the innermost open loop if that is a `REPEAT`, otherwise it opens an `UNTIL … UEND` loop** (so such a loop can't be opened directly inside a `REPEAT` body; use `WHILE`). A closing statement that doesn't match the innermost loop is "NEXT without FOR" / "WEND without WHILE" / "UEND without UNTIL"; an unclosed loop at the end is "FOR without NEXT" / "REPEAT without UNTIL" / "WHILE without WEND" / "UNTIL without UEND".
- **`AGAIN [n]`** restarts the body of the n-th innermost open loop (default 1) from its first statement, without testing the condition or stepping the `FOR` variable (a branch to the body start). Loops opened outside a function body are not visible inside it ("AGAIN without loop").
- **`END`** branches to the end of the program (a fixup resolved at the end of code generation; inside a direct mode line it ends that line). `END IF`, `END UNLESS` and `END FN` are not `END` statements (the parser looks ahead).
- **`POP`** discards the latest return address (`DROP.C`); with no pending `GOSUB` it is "Return stack underflow" at run time. (Don't use it inside a function: calls keep their return address and context there too.)
- **`ON n GOTO|GOSUB t1,t2,…`** jumps to the i-th target if `i <= n < i+1` (the fraction is cut off); for any other value it does nothing. `GOSUB` returns to the statement after the `ON`. Targets can be line numbers or labels. The value is kept in a hidden variable `@ON<k>O`.
- **Parser fixes made for this:** the `IF` nodes (single- and multi-line) now carry the condition expression as their first branch (it was dropped), and a multi-line `ELSE` now consumes the end of line after it.

## Runtime (`runtime.[ch]`)

`init_runtime` wires `varmem_t` and `codegen_t` to the runtime's `report`/`halt`. (The former `basintp` token interpreter stub was removed: the BASIC system compiles, it does not interpret.)

### INPUT, GET (`cgendecl.c`, `vm.c`)

- **`INPUT [#ch,] ["p";] v1, v2, …`** generates `<channel> PCHN`, `INPL`, then per variable `INPN` (numeric) or `INPS` (string) followed by the usual store (`cgen_from_varref_lvalue`), and finally `INPE`. The prompt text (plus `? ` unless a comma followed the prompt) is a constant in the data segment; it is the parameter of `INPL`. Without `#ch` the code pushes 0 and does `PCHN`, because the output channel set by `PCHN` is sticky in the VM (`PRINT` does the same via `cgen_gen_channel0()`; `vmtest1` tags output on non-zero channels as `[#n]`).
- `INPL` prints the prompt through the print callback and reads a line with `vm->input( vm, userdata, channel )` (malloc'd line without newline, or 0 = end of input; default: stdin). The host is expected to echo the typed line; the VM sets the output column to 0. The line stays in `vm->inbuf` with a field cursor (`inpos`). `INPN`/`INPS` take the next field; when that fails they print `?Redo from start` and set `pc` back to the `INPL` (`vm->inredo`), so the prompt is shown again. `INPE` prints `?Extra ignored` if fields are left and frees the line (also freed by `vm_clear_stacks()` after errors).
- **`GET [#ch,] v1, v2, …`** generates `<channel> PCHN` and per variable `GETK` (pushes a one-character string; waits for the key via `vm->getkey`, else polls `vm->inkey` every millisecond, else `getchar()`), plus `ASC` for a numeric variable, then the store.
- `vmtest1` feeds `INPUT` lines (separated by `\n`) and `GET` characters from the same test input string as `INKEY$`.

### Host wiring (`basrepl.[ch]`, `engine1999.c`, `sdlscreen.c`)

- **`repl_t`** (`basrepl.[ch]`, no SDL) owns the runtime, compiler, program store and one *persistent* `vm_t`. `repl_enter( repl, text )` takes one input line: `preprocess_buffer` (upper case outside quotes), then tokenize (`NEW`, `RUN`, `LIST`, `LOAD`, `CLEAR` are statements, no host level commands); a numbered line goes into the program (`enter_line`; a number alone deletes the line), an unnumbered one is compiled and run at once, appended to the code segment (`vm_run_at`), so variables, user functions and the DATA pointer survive from line to line. When the line has run (or failed), `repl_execute()` discards its code and data again with `cgen_rollback()` (the code and data size from before the line; the table of shared constants is rebuilt without the discarded ones) unless the line stored something that points into them: `DEF FN` (the function variable gets the code offset), `LABEL` (the label variable) and `DATA` (records chained in the data segment) call `cgen_note_persistent()`, and a changed `codegen_t.persistent` counter keeps the line. This also holds for a line that fails after such a statement (the function stays defined). A long session of ordinary lines therefore doesn't grow the segments. `RUN [line|label]` (a statement) clears the runtime, compiles the whole program and runs it from the start (`vm_run`) or from the target (`vm_run_at`); the variables stay afterwards. A `DATA` line entered after the last item was read moves the pointer to the new items. All error texts (compiler, code generator, variables, VM) go to `repl->report`, always ending in a newline; compiler/variable-store/code-generator halts `longjmp` to a `jmp_buf` inside `repl_execute()`.
- **MONITOR** (`NT_MONITORSTMT 0x64`, token `MONITOR` 147, instruction `MON 0x141 ( -- )`, `cgen_from_monitorstmt` in `cgenprog.c`): like `NEW` the VM stores a request (`VMREQ_MONITOR`) and ends the run; `repl_finish()` sets `repl_t.monitor` and the host opens the monitor. `repl_compile()` (compile the stored program without running it) and `repl_vm_start( addr )` / `repl_vm_resume( step, breakpoints, n )` (suspend the VM at an address with the code segment as it is, then continue it or run one instruction; a run that ends is finished like after `RUN`) serve the monitor. `vm_begin()` / `vm_resume()` in `vm.c` are the resumable run (see the top of `vm.h`): breakpoints, `BRK` with `vm_t.debug`, single-step.
- **Program commands** (`cgenprog.c`, nodes `NT_LOADSTMT 0x5C`, `NT_RUNSTMT 0x5D`, `NT_LISTSTMT 0x5E`, `NT_NEWSTMT 0x5F`, `NT_CLEARSTMT 0x60`; instructions `LOAD 0x139 ( s -- )`, `RUNP 0x13A ( s n -- )`, `LIST 0x13B ( s1 n1 s2 n2 -- )`, `NEW 0x13C`, `CLR 0x13D`, `DELE 0x13E ( s1 n1 s2 n2 -- )`, `RENM 0x13F ( s1 n1 s2 n2 step -- )` with nodes `NT_DELETESTMT 0x61`, `NT_RENUMSTMT 0x62`; the last two call the host (`vm->deletelines`, `vm->renumber`, implemented in `basrepl.c` with `delete_lines()` and `renumber_program()` of `baspgm.c`) and end the run (`pc` = end of the code) because the program they changed no longer matches the code. `renumber_program()` maps the numbers of the selected lines, then rebuilds the program line by line from the detokenized text: `renum_text()` scans it (skipping strings, backtick literals and comments) and rewrites the numbers after GOTO/GOSUB/GO TO/GO SUB (comma lists), THEN, ELSE, RESTORE, RUN, and the ranges of LIST/DELETE; a line whose text did not change keeps its tokens (only the number in the header changes), a changed one is tokenized again; the new program replaces the old one only if everything worked; `EDIT` (node `NT_EDITSTMT 0x63`, instruction `EDIT 0x140 ( s n -- )`, same operands as `RUNP`) is a fourth request kind, `VMREQ_EDIT`: `repl_finish()` calls `repl_edit_line()`, which finds the line (a label via `find_label_line()`), detokenizes it and hands the text to the host callback `repl_t.edit` (the line editor); the edited text is stored in `repl_t.pending` and entered like a typed line by `repl_enter()` / `repl_run()` afterwards (`repl_enter_pending()`, a loop, because an edited line may be an `EDIT` again) - ESC = the callback returns 0 = no change; `EDIT` without a target reports "Not implemented yet"; `NEW` is a third request kind, `VMREQ_NEW`: `repl_finish()` calls `repl_new()` and does not restart anything. `CLR` is done inside the VM by `vmem_clear_vars()`, which skips labels, functions and the hidden compiler variables named `@…`, e.g. the limit/step of a FOR): a target is passed as *label name* (`""` = none) plus *line number* (`-1` = none), because the program is recompiled and the variable numbers change. `LOAD` and `RUNP` can't be done by the VM (it would replace the code it runs): they store `vm->request` (`VMREQ_LOAD` / `VMREQ_RUN`), `vm->reqname`, `vm->reqline`, set `pc` to the end of the code and so end the run normally. `basrepl.c` (`repl_finish()`) then carries the request out: LOAD reads the file (`repl_load_program()`: binary via `read_program_header()`, else text lines; into a scratch `program_t` that replaces the stored one only on success), RUN/LOAD clear the runtime, recompile the stored program and start the VM at the program start (a `LOAD` typed in direct mode, `repl_finish( …, direct )`, only loads and clears the runtime; `RUN` compiles later), the line (`cgen_find_line()`) or the label's code offset (the label variable of the new compile). This is a loop, not a recursion, so a program ending with `RUN` doesn't grow the stack; as such short runs never reach the VM's own interrupt polling, `repl_finish()` polls `interrupt` before every chained restart ("Break"). `LIST` is a callback (`vm->list`, set by the REPL to `repl_vm_list()`) that prints with `list_program()` to `vm->channel`; labels are turned into lines by `find_label_line()` (`baspgm.c`), which scans the detokenized lines for `LABEL name` (skipping strings, backtick literals and `'` comments). A single `LIST` target means that line only (codegen passes it as both ends). A host that ignores `vm->request` just sees the program end (`vmtest1` prints the request).
- The host sets the callbacks `report print inkey input getkey interrupt save` of `repl_t` (the VM ones have the signatures of `vm.h`; their user data parameter is the `repl_t*`, host data goes into `repl_t.userdata`). `repl_save_program()` implements `SAVE` for a host. `vm->interrupt` is polled every 4096 instructions and when `INPUT`/`GET` get nothing: true stops the program with "Break".
- **Threads:** the SDL screen renders in a worker thread; the REPL and the VM run in the main thread. `engine1999.c` maps the callbacks onto `sdlscreen.c`: `print` → `sdlscr_puts` (channel 0 only; other channels are discarded, there are no devices yet), `input` → `sdlscr_lineinput` (the line editor echoes; stop event `SDLEV_BREAK`), `getkey` → `sdlscr_getkey` (waits), `inkey` → `sdlscr_pollkey` (never waits), `interrupt` → `sdlscr_breakrequested`. While a line runs, `sdlscr_pollkeys( true )` makes the screen thread queue keys (no cursor); then **ESC is the break key** (sets a flag and raises `SDLEV_BREAK`, it is not delivered as a key). Key codes: printable ASCII, 13 RETURN, 8 BACKSPACE, 9 TAB; other keys (cursor keys, function keys, non-ASCII text) are ignored for now. Closing the window also breaks the program.
- Debug output (token bytes, detokenized text, parser tokens, syntax tree, emitted instructions) is controlled by `basdbg_flags` (`basdebug.h`), off by default; `engine1999` sets it from `--debug-*` options (see `build-and-test.md`).
- Error messages start on a fresh line (`host_newline()`); `Ready.` follows every non-empty input line except a numbered program line (entered or deleted).
- Tested by `repltest1` (headless) and, for the screen/keyboard part, by running `engine1999` under `Xvfb` + a window manager with keys injected through XTest (the test scripts are not part of the repository).
