## 4. Host polish (`engine1999.c`, `basrepl.[ch]`, `sdlscreen.c`)

- [x] The prompt line is limited to 4095 characters in both hosts (2026-11-01, owner's decision; `PROMPT_BUFSIZE` in `engine1999.c`, `CON_PROMPTMAX` in `engine1999c.c`). A screen holds fewer: the editor leaves one row free, so a window of 80 x 25 takes 1919 characters at most (a terminal as many as `columns x (rows - 1)`); a redirected input takes the full 4095. Longer lines would need a horizontally scrolling editor (not planned)
- [x] (all steps done; the encoding of `.bas` listings too: UTF-8, item 15) Cursor keys and function keys for `GET` / `INKEY$`: **designed 2026-10-31, owner's decision** (`docs/basic-language.md`, "Keyboard: cursor keys, function keys, the character set"): keys that are not one byte arrive as xterm style ANSI escape sequences (`ESC [ A`...; F1 = HELP, reserved), ESC pressed twice = break, PAUSE/BREAK = immediate break, a sequence that stalls is dropped after a short time (console host); character set ISO-8859-15, the font gets the printable glyphs 160..255 and control glyphs for 127..159, typed `ä ö ü ß €` are mapped to it. ## 12. Running without a GUI (scripting) *(wish of the owner, 2026-10-31; **implemented**: `engine1999c`, `docs/console-host.md`; leftovers below)*

Goal: use Engine1999 in shell scripts and on servers without a window: `engine1999c prog.bas`, `echo 'PRINT 1+2' | engine1999c`, a `#!` line, output on stdout, errors on stderr, exit codes, no SDL needed at run time.

**Would the current code support it? Largely yes**, because the core never learned about SDL: `grep` finds no SDL or `sdlscr_*` in the tokenizer, parser, code generator, VM, REPL (`basrepl`), variables, `iodev`, `basfiles`, `gfxcore`/`gfxops` (the table), `synth`, `mml`, `ansi`, `vmasm`. Everything the program sees of the machine goes through callbacks (`repl_t`: `print`, `printn`, `report`, `inkey`, `input`, `getkey`, `interrupt`, `save`, `sound`, `gfx`, `hlstyle`, `edit`, `pause`), and `vmtest1` and `repltest1` already run complete programs with screenless test hosts. Only `engine1999.c` (the GUI host), `fulledit`, `monitor`, `sdlscreen` and friends need SDL. `BYE`/`QUIT [code]` (done) gives the exit status; an error could end the process with 1.

Done (2026-10-31, first version, `docs/console-host.md`): **the console host `engine1999c`** (`engine1999c.c`, no SDL; run mode, stdin mode, interactive prompt on a terminal, Break from Ctrl-C, single keys on a terminal, exit codes 0/1/2/`BYE n`), the `#!` first line in text program files, and the display statements (`CLS`/`LOCATE` as ANSI sequences, the other graphics statements fail with "Not available in the console host", sound silent). `contest1` tests it (44 checks).

Done (2026-10-31, second stage): **program arguments and environment** (`ARGC`, `ARG$(n)`, `ENV$(name$)`; `engine1999c prog.bas a b`, built programs get their command line too) and the **standard channels** `stdin:`, `stdout:`, `stderr:` (`docs/basic-language.md`, "Program arguments and the environment").

What is still missing:
- [x] ~~**HIGH PRIORITY: `BUILD` for headless programs**~~ done (2026-10-31): `BUILD name$ [, WINDOW | CONSOLE]`; the console kit is `engine1999c.o` (it contains the console twin of `run_embedded()`), needs only the C and math libraries; `engine1999c` builds console executables by default. `buildtest1` links and runs one (34 checks), `contest1` too.
- [x] ~~**HIGH PRIORITY: syntax colored `LIST` in the console host**~~ done (2026-10-31): `ansi_hlstyle()` moved to `ansi.c`, `--color[=always|never|auto]`, `NO_COLOR`; `FILES` is colored with it. Not tested through a real pseudo terminal (`--color=always` forces the colors in `contest1`).
- [x] ~~**Full-screen `EDIT` and `MONITOR` for interactive console use**~~ done (2026-10-31, owner's request): both editors run on a *screen driver* (`scrdrv.h`) with a window backend (`sdlscreen.c`) and a terminal backend (`engine1999c.c` + `conscr.[ch]`: alternate screen, incremental painting, truecolor / 256 colors from the palette, no curses); the layout follows the screen size and a terminal resize (`SIGWINCH`) is honored; see `docs/console-host.md`. Not done: mouse, a wrapped line in the monitor's prompt on very narrow terminals.
- [ ] **Audio without a window** (optional): the audio device could be opened alone (`SDL_INIT_AUDIO`) for scripts that `PLAY` music; `SDL_VIDEODRIVER=dummy` runs the *current* GUI host without a window, but its input and output still go to the invisible screen, so it is no substitute.
  - **Console audio client via ALSA with file I/O only** (owner's idea, 2026-11-07, recorded, not started): ALSA's PCM devices (`/dev/snd/pcmC*D*p`) can be operated with plain `open` / `read` / `write` plus `ioctl` (`SNDRV_PCM_IOCTL_HW_PARAMS`, `SW_PARAMS`, `PREPARE`, `START`, `DROP`; the kernel interface, no `libasound` and no SDL), so `engine1999c` could play sound without any library, and `BUILD` console executables stay `ld`-only. Proposed structure: a generic **`audio:` driver** (in the `iodev` style, `docs/io-subsystem.md`) that forwards the PCM data to a physical back end chosen by the host it runs on: **`sdlaud:`** (the existing `sdlaudio.[ch]`, window host) or **`alsafio:`** (the new file-I/O ALSA back end, console host). The synthesizer (`synth.[ch]`, no SDL) and everything above it (`SOUND`, `PLAY`, `SFX`, the editors) would then use one interface and be unaware of the back end.
  - **Open question, to be answered before starting: does this make sense, is it feasible?** Points known so far: (1) SDL audio is *pull* (the device calls a callback that fills a buffer), ALSA through file I/O is *push* (a thread must `write()` blocks, blocking until the ring buffer has room); the driver would hide that, e.g. `alsafio:` runs its own thread that calls the same fill function the SDL callback calls, and the SDL back end keeps its callback, so the interface above both is "fill( buf, frames )" (a pull model; the thread of `alsafio:` is the adapter). The other direction (SDL thread, as the owner suggested) is possible too: a thread owned by the driver that pulls from the callback side and writes; it would be needed only if a back end must push. (2) Threads: the engine has a rule of no pthreads / mutexes outside SDL (`docs/display-engine.md` "Threading": atomic words); the console host has no SDL, so `alsafio:` needs `pthread` (or `clone()`), which has to be reconciled with that rule and with `BUILD` (only `ld`, kit = `engine1999.o` + `engine.lib`; pthread is part of libc on current glibc, check old ones). (3) The raw ALSA ioctl interface is not as stable / documented as `libasound` (hw_params negotiation by masks and intervals, sample formats, period / buffer sizes, xruns); PulseAudio / PipeWire systems usually hold the hardware device, so `/dev/snd` direct access may fail (device busy) or need the `alsa-pipewire` plugin, which exists only in `libasound`: **the file-I/O back end may work only on systems without a sound server** (check with a prototype; `/dev/snd/pcm*` permissions: group `audio`). (4) Latency and timing: events are currently queued with ~1 ms accuracy and mixed in the audio callback; a pushing thread must keep a block ahead like the callback does. (5) Policy: opening `/dev/snd` is outside the program's folder (item 54, `docs/security-policy.md`), the driver is trusted code of the host, not a program-visible device. Next step if the owner says go: a small prototype that plays a sine through `/dev/snd/pcmC0D0p` with the ioctls (no engine code), to see whether hw_params / write work on the owner's machine, then decide.

## 14. A terminal emulator screen and a Claude screen *(owner's idea, 2026-11-01; nothing decided or started)*

The idea: a text screen of the Engine that is a terminal emulator, and a text screen for Claude, perhaps both on **one terminal emulation module**. My opinion, for the discussion:

- **The terminal emulator is a good fit and worth doing**, in this shape: a module `vt.[ch]` (no SDL, like `ansi.c`) that is the *model*: a state machine that eats bytes (VT100 / xterm subset: cursor movement and addressing, erase, insert / delete of characters and lines, scroll regions, `SGR` with 16 / 256 / true colors, the alternate screen, `DECSET` modes for the cursor and the mouse reports, `OSC` titles) and writes into a text screen through a small callback table; and a **pty front end** (`forkpty`, a child shell, resize with `TIOCSWINSZ`, `SIGCHLD`). It is testable without a window (`vttest1`, like `ansitest1`: byte streams in, cell contents out). The keys need no new code: `keyseq.c` already makes the canonical xterm sequences, which is what a pty wants. The text screen has runtime sizes since the console host, and the screen driver table (`scrdrv.h`) can carry it: a new screen (`TXTSCR_NSCREENS` 3 to 4) entered with a statement or key (an extension word: `TERM`?) and left with a key that the Engine keeps for itself. A BASIC-level cousin falls out of it: a `pty:` driver, like `sh:` but interactive (`OPEN "pty:bash" ...`).
- **The Claude screen should not be a second big feature at first.** The cheap, honest version is **the terminal emulator running `claude` (Claude Code)**: the integration is then a command line, and everything it needs (streaming, markdown, tools, the login) is somebody else's code. A native chat screen would need TLS (the `tcp:` driver has none: a new dependency, or a helper process), the API with streaming, JSON, key handling, markdown rendering in an 80 x 25 text screen, tool calls and, above all, **permission questions** (an AI that edits and runs programs on the user's machine): that is a project of its own. So I would **share the module only in the sense that the Claude screen is a client of the emulator**, not a second implementation of terminal handling. A chat screen that just prints text needs `ansi.c`, not a terminal.
- **Things to decide first** (*decision*): (1) the **character set**: the font is ISO-8859-15 with control glyphs; real terminal programs speak UTF-8 and use box drawing, block elements and arrows, which the font lacks (a second glyph page, or a mapping of the box drawing characters onto redefined characters, or accept `?`); (2) the **window size**: the window is a fixed 80 x 25 text screen; the emulator wants more (a resizable text screen on a bigger layer, or scrolling windows), and `htop` or `vim` at 80 x 25 are fine, a wider one is better; (3) **security**: a shell inside a program-controlled window is shell access; it must be opt-in and go through `iodev_allowed()` (item 3, sandboxing), and a `BUILD` executable must not get it silently; (4) the license exception and the dependency policy (no new libraries: `forkpty` is in glibc's `libutil` / `libc`, fine); (5) in the console host the emulator is a terminal in a terminal, useful for little: window host first; (6) whether a Claude screen needs a network permission and a place for the API key, and what the user is told before anything is sent anywhere.
- **Order**: the joystick (item 4) first; then `vt.[ch]` with its test and the `pty:` driver (useful by itself, small); then the emulator screen; then the `claude` launcher as a convenience on top. A native Claude chat screen only if the CLI turns out not to be enough.
