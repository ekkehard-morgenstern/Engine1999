# The 3D mesh renderer `M3D`

*2026-11-14, owner's decision: the sector renderer (`W3D`, `docs/3d-subsystem.md`) cannot express Deqq's House II (a town round a house, tall things seen over fences, rooms over rooms), so a renderer without sectors was written next to it. The sector renderer stays for the other demos (Manor, Bug Hunt, the showroom, Deqq's House I). This page is the reference for the new one; the code is `m3d.[ch]` (no SDL, no global state), the test is `m3dtest1.c`.*

> The sector renderer `W3D` (`docs/3d-subsystem.md`) stays: it is a supported feature with its own demos (Manor, Bug Hunt, Showroom, Deqq's House I, Y2K38's server room, the map editor), and nobody plans to remove it (owner, 2026-11-14). Which renderer fits depends on the world: sectors are fast and simple for rooms joined by portals; meshes can put anything anywhere.

## Model

- A world is a set of **objects** (0 .. 16383). An object is a triangle mesh with a position, a heading (yaw about the z axis), a light level (0 .. 255) and flags. The mesh is in the object's own coordinates; `M3D OBJPOS o,x,y,z[,yaw]` moves and turns it (a door is an object that turns about its hinge).
- **Things** (0 .. 1023) are billboards: a picture of a given width and height that always faces the viewer, with its bottom at `z`.
- Coordinates: x east, y north, z up; angles in degrees, 0 = +x, 90 = +y; to the right of the view direction is clockwise. A triangle is **counterclockwise seen from its front** (the normal `(b-a) x (c-a)` points to the viewer); one-sided objects do not draw or collide with the back. `M3D OBJECT o,16` (two sided) draws both sides.
- Pictures are `GFX GRAB` blocks (`M3D TEXTURE n,a$`, as for `W3D`); palette index 0 is see-through where the object is masked (flag 1) or translucent (flag 2) and always in things. A picture number with no picture draws that palette color flat.
- `M3D BOX o,x1,y1,z1,x2,y2,z2,tex[,faces]` adds the faces of a box (picture coordinates 1 texel = 1 unit, anchored to the object, so neighbouring boxes match; `faces` is a bit mask of the sides to build: 1 +x, 2 -x, 4 +y, 8 -y, 16 top, 32 bottom, default 63 = all, so a box can leave out a side that a quad with another picture covers: a house front with a door). `M3D VERTEX o,x,y,z[,u,v]` numbers vertices from 0 per object; `M3D FACE o,a,b,c,tex` and `M3D QUAD o,a,b,c,d,tex` add triangles; without `u,v` the picture coordinates follow the position by the direction of the face.
- Object flags: 1 masked, 2 translucent (mixed half and half, drawn last, far to near), 4 **passable** (no collision and no floor or ceiling), 8 **see-through** (shots, `USE` of walls and sight pass: glass, a railing), 16 two sided.

## Drawing

Every triangle is culled (back face, behind the viewer, off the screen), clipped against the near plane (2 units) and rasterized with a z buffer and perspective-correct picture coordinates; the light level of the object, the lamps (`M3D LAMP n,x,y,z,radius,amount`, up to 8, per pixel, brightening only) and the fog (`M3D FOG d`: dark at distance d) pick a row of the color map (`M3D COLORMAP` builds it from the palette). Order: the sky (`M3D SKY`, a picture around the viewer by angle), opaque and masked objects, things (far to near, depth tested), translucent objects (far to near). `M3D FAR d` skips what lies beyond d. Cost: about 1.6 ms for a test scene at 320 x 150 (`M3D VIEW x,y,w,h,2`).

## Collision, floors, rays

The player is a vertical capsule (`M3D PLAYER radius,height,eye,step`, default 14, 56, 46, 24), `M3D CAMERA x,y,z,yaw[,pitch]` puts the **feet**. `M3D MOVE forward,right` moves in small pieces, pushes the capsule out of the triangles it touches (spheres at the middle heights; everything lower than `step` above the feet is walked over), slides along an axis when blocked, refuses a floor more than `step` higher, refuses a ceiling lower than the player's height, and then lets the feet follow the floor (`M3D("FLOORZ")`, `M3D("FLOORAT",x,y,z)` = the highest surface at or below z, `("CEILAT",x,y,z)` the lowest above). `M3D LIFT h` raises the feet above the floor (a jump: steps up to `step` above the raised feet are taken). `M3D("HIT")`: 1 = something pushed, 2 = no movement at all.
Rays use the same triangles: `M3D("SHOOT",range)` (things and objects, the last shot is in `SHOTKIND` 0 / 1 object / 2 thing, `SHOTOBJ`, `SHOTDIST`, `SHOTX/Y/Z`), `M3D("USE",reach)` (the object in front, whatever its flags), `M3D("SEES",n)` (a thing's line of sight to the eye).

## Zones, walking things, the world document

- **Zones:** `M3D ZONE id,x1,y1,x2,y2,z1,z2[,tag]` names a box of space for the game (a room); `M3D("ZONE",x,y,z)` is the id of the first zone that contains the point (z within z1 - 2 .. z2), -1 if none, `M3D("ZONETAG",x,y,z)` its tag. The renderer does nothing with them. Put the zones of an upper floor and of a chair or table you can stand on *before* the zones below them. `M3D CLEAR` deletes them.
- **`M3D THINGMOVE n,dx,dy`** walks a thing like `M3D MOVE` walks the player (a body of radius 0.4 x width, at most 14, the player's step height; it follows the floor); `M3D("HIT")` tells whether a wall pushed it.
- **`M3D WORLD`** builds the world from the current JSON document (`JSON LOAD` first), replacing objects, things, lamps and zones; pictures and settings stay:

```
{ "format": "e99-mesh-world", "version": 1,
  "environment": { "fog": 4200, "sky": 11 },
  "start": { "x": 1730, "y": 1570, "z": 0, "angle": 90 },
  "zones":   [ { "id": 12, "name": "living room", "box": [x1,y1,x2,y2], "z": [z1,z2], "tag": 0 } ],
  "things":  [ { "id": 400, "tex": 282, "x": .., "y": .., "z": 0, "w": 32, "h": 76 } ],
  "objects": [ { "id": 12, "name": "..", "flags": ["masked","translucent","pass","seethru","twosided"] | number, "light": 255, "pos": [x,y,z], "yaw": 0,
                 "boxes": [ [x1,y1,z1,x2,y2,z2,tex[,faces]], .. ], "quads": [ [x,y,z, x,y,z, x,y,z, x,y,z, tex], .. ] } ] }
```

Errors name the element (`objects[3].boxes[1] needs 7 numbers`). `name` and `note` are free text the loader ignores.

## Deqq's House II on the mesh renderer

Since 2026-11-14 `demos/deqq2.bas` runs on `M3D` (`demos/deqq2.mesh.json`, the source of its world). The first version of the document was converted from the sector document `demos/deqq2.world.json` (which stays: the sector renderer's loader and `worldtest.sh` still use it): **every room became an object with the room's number** (a floor slab, a ceiling slab where there is one, walls 8 thick inside the room where there is no opening, lower and upper wall pieces round an opening between rooms of different heights, floor and jamb pieces across the gap between rooms), windows and railings are separate objects (ids 1000 + the opening's number: masked or translucent panes; 1500 +: invisible rails; 2000 +: fences), the doors 6, 7, 8 and 33 are leaves that turn about their hinge (`M3D OBJPOS`), 3000 is the garden gate (`M3D OBJSHOW`), 51 the chair platform, 600 the ground (with holes where the cellar lies), furniture and houses are boxes. Rooms of the old document are the zones. `M3D OBJLIGHT room,level` darkens or lights a room. Facts found while doing it: floors and ceilings are 1 unit thick so a floor above a room does not lower it; a thing that stands on furniture needs the furniture's top as its level (`TLZ` in the game's `OBJDATA`: values from 3 up are used as they are, 114 / 226 are the upper floor and the attic: `M3D("FLOORAT",x,y,z)` takes the highest surface at or below z, and the ceiling slab of the room below is at 112 .. 113); the test hooks of `deqq2test.sh` take the same hints (`goto x y angle z`).

## Not done yet

Rotation about other axes (an object turns only about z), true tilt, per-vertex colors, texture animation / scrolling, the hardware path, a mesh file format, fast culling for very large worlds (all objects are visited each frame and each ray; fine for a few thousand), speed tuning. Missing for Deqq's House II: the light effects (flickering cellar, pulsing crash site) and the scrolling water, the pond is a still picture; the generated world is a first conversion (walls are 8 thick inside the rooms, so openings are as wide as before but rooms are 16 narrower: a hand-made mesh world would look better).

## Renderer interface

The module is split into the world model (`m3d.c`: objects, things, lamps, camera, collision, rays, the operations and queries) and a renderer behind the interface `m3drend_t` in `m3dpriv.h` (`create`, `destroy`, `resize`, `palette`, `render`). The model owns the palette and everything that behavior depends on, so a query answers the same whatever draws. The software rasterizer is `m3dsoft.c` (`m3d_soft_renderer`; its color map, translucency table, bitmap and depth buffer are its own). A second backend (OpenGL 2, 32 bit ARGB output) is planned; see `SESSION.md`.

### Choosing the renderer (`M3D SOFTWARE`, `M3D HARDWARE`)

`M3D SOFTWARE` switches to the software renderer (always possible, the default). `M3D HARDWARE` switches to the OpenGL 2 renderer; where there is none it is the error "Hardware renderer not available". `M3D("RENDERER")` is 0 or 1 for the one in use, `M3D("HWAVAIL")` is 1 when `M3D HARDWARE` can succeed (a program asks before it switches). `M3D RESET` keeps the choice; the palette and the view carry over a switch. The model (`m3d.c`) does not know OpenGL: the window host registers the hardware renderer with `m3d_set_hardware()` (`m3dgl.[ch]`: `m3d_gl_renderer()`); the console host registers none. Switching builds the new renderer's state first, so nothing changes when that fails. `m3dtest1` tests the switching with a stand-in renderer.

**Status: the renderer exists** (`m3dgl.c`, step 4); the choice in the 3D preferences and the default (hardware when `M3D("HWAVAIL")`) exist since step 5: `W3K_MESH` in `w3dkit.lib` selects the hardware renderer when it is available, `prefs3d.lib` has a **Renderer** row (Software / Hardware, saved as the sixth line of `local:3dprefs.cfg`, shown only for programs that use `W3K_MESH` when hardware is available).

### The OpenGL binding (`glload.[ch]`)

No GL library is linked. SDL opens the system's library (`SDL_GL_LoadLibrary`) and hands out addresses (`SDL_GL_GetProcAddress`); `glload_bind()` keeps the 60 functions the renderer needs (GL 1.1 drawing and textures, buffers, GLSL shaders, framebuffer objects under the core, ARB or EXT names) in a `glapi_t` while a context is current; one missing function means "no OpenGL 2". `glload_probe()` runs once in the screen thread when the window opens: it makes a hidden window and context, binds, reads `GL_VERSION` (>= 2.0), destroys them again and gives the current context back to the SDL renderer; the result is an atomic state (`glload_state()`, `glload_info()` with the version, the renderer's name and the reason for a "no"). `ENGINE1999_NOGL=1` skips the probe (answer: no). `gltest1` (in `make check`; skipped without a display or without OpenGL 2, `GLTEST_REQUIRE=1` makes a skip a failure) checks the probe, the binding and real drawing: a shader fills a framebuffer object and `glReadPixels` returns it (seen with an NVIDIA driver and with Mesa's llvmpipe under Xvfb).

### Pictures: palette bitmap or ARGB

A renderer says in `m3drend_t.argb` what its picture is. The software renderer makes a palette bitmap (`m3d_render()`, copied into the target layer by `sdlscr_gfx_putbuf()`); a hardware renderer makes 32 bit ARGB (`m3d_render32()`; `m3d_render()` returns 0 for it and the other way round, `m3d_is_argb()` tells which) and the window host puts it into the 32 bit layer, `sdlscr_3d_put()` (`docs/graphics-subsystem.md`). The colormap and the translucency table are software only; a hardware renderer lights and blends in true color.

### The hardware renderer (`m3dgl.c`)

**Where it runs:** on the thread that calls `M3D RENDER` (the program thread), with an OpenGL context of its own on a hidden window (made at `M3D HARDWARE`, deleted when the renderer is left or the module freed); the context is made current again at each frame if another thread had it. The screen thread, its SDL renderer and the probe are not involved, there is no hand-over of a context between threads. If the program thread ever changed while the context is current on the old one, switching would fail (not seen: the VM runs on one thread). The picture goes into the 32 bit layer by the host, `sdlscr_3d_put()`.

**What it draws, in this order** (as the software renderer): the sky (a fullscreen triangle whose shader looks the picture up per pixel from the view direction exactly as `draw_sky_bg()` does, or a flat clear color), the opaque objects (collected per frame on the CPU: visibility by bounding sphere and back faces culled as in the software renderer, triangles sorted by picture so that there is one draw call per picture and masked flag; world coordinates are uploaded, the vertex shader makes the view and the projection with the same pinhole camera, the near plane 2 and a far plane from `M3D FAR`; the picture is rendered upside down so that the first row read back is the top one), the things (a rectangle facing the viewer at the depth of the thing's middle, back to front, no depth write), the translucent objects (back to front, mixed half and half). **Pictures** are uploaded once as 8 bit index textures (`GL_LUMINANCE`, nearest, repeating; again when `tex_t.gen` changed), the palette is a 256 x 1 texture and the fragment shader looks the index up in it (index 0 of a masked picture is discarded); a flat-color face uses an identity texture. **Light:** the object's light plus the lamps' light at the point (`amount * (1 - distance / radius)`), times the fog (`1 - depth / fog`), as in the software renderer, but as a smooth factor on the true color instead of 32 steps and the nearest palette color. **Palette:** the host hands the target layer's palette over before each frame (`M3D COLORMAP` is not needed in hardware mode; a palette fade shows at once).

**Tests:** `m3dgltest1` (in `make check`, skipped without display or OpenGL 2) draws ten scenes with both renderers (plain, light, fog, lamp, flat and picture sky, masked, translucent, things, camera) and compares them pixel by pixel on a ramp palette: at most a few percent of the pixels may differ (the measured mean difference is below 1.2 of 255; the differences are edge pixels); it also checks that a changed view and a changed picture reach the hardware renderer. `m3dglhost.sh` (in `make hosttest`) runs the real window host under Xvfb: a typed-in program draws a scene with the software renderer, switches with `M3D HARDWARE`, draws again and switches back, and the screenshots are compared (the two pictures were identical byte for byte).

**Speed (measured 2026-11-14 under Xvfb, where OpenGL is Mesa's CPU renderer llvmpipe, so the hardware numbers say little about a real GPU):** Deqq's House II at 640 x 264, 120 frames turning in place at four places: software 2.4 .. 4.3 ms per frame (150 .. 2260 triangles drawn), hardware 4.3 .. 13 ms (320 .. 3240 submitted). **On the owner's machine (NVIDIA GT 710, 2026-11-14) the hardware renderer is faster:** software 2.2 .. 4.3 ms per frame, hardware 1.7 .. 2.1 ms (about 2 times, and nearly independent of the scene: the readback and upload dominate, not the triangles). **Scale 1 on the owner's GT 710 (2026-11-14):** hardware 2.2 .. 2.9 ms per frame at 640 x 264 (1.8 .. 1.9 ms at 320 x 132), software 7.2 .. 14.3 ms (2.2 .. 4.2 ms at 320 x 132): at the full size hardware is 3 to 5 times faster, and software at 14 ms is near the 16.7 ms frame budget. **Scale 1 (640 x 264 instead of 320 x 132), Xvfb / llvmpipe:** software 7.1 .. 14 ms per frame (3.5 times slower), hardware 8.3 .. 10 ms (CPU-emulated GL, so not meaningful); the real GPU's numbers: see `m3dbench.sh` (it now measures both scales). **The 3D preferences have the render size option (320 x 132 or 640 x 264; default 640 x 264 with hardware).**

**`sh m3dbench.sh` repeats the measurement on any machine** (it opens the window; type `LOAD "demos/deqq2"` and `RUN`; the program `BENCH` in `deqq2.bas` runs when the environment variable `DEQQ2_BENCH` names an output file). Per frame the hardware path collects the triangles on the CPU, sorts them, uploads and reads the picture back (`glReadPixels`), so on a fast machine it is not automatically quicker than the software renderer; not measured on a real GPU.

**Not done / differences:** no vertex caching (the triangles are collected again every frame), no clipping of the object list by a spatial structure. The three differences of the first version are gone (2026-11-14): `M3D("DRAWN")` counts the same triangles as the software renderer (what is left after clipping at the near plane; things are not counted by either), index 0 of a plain picture and a missing sky (no color, no picture) are see-through (the picture's alpha is 0 there and `sdlscr_3d_put()` leaves such pixels transparent, so the layers below show, as with software; ARGB renderers must set the alpha: 0 = transparent, anything else = opaque). The light is smooth, so hardware pictures have no banding.
