# The 3D mesh renderer `M3D`

*2026-11-14, owner's decision: the sector renderer (`W3D`, `docs/3d-subsystem.md`) cannot express Deqq's House II (a town round a house, tall things seen over fences, rooms over rooms), so a renderer without sectors was written next to it. The sector renderer stays for the other demos (Manor, Bug Hunt, the showroom, Deqq's House I). This page is the reference for the new one; the code is `m3d.[ch]` (no SDL, no global state), the test is `m3dtest1.c`.*

> The sector renderer `W3D` (`docs/3d-subsystem.md`) stays: it is a supported feature with its own demos (Manor, Bug Hunt, Showroom, Deqq's House I, Y2K38's server room, the map editor), and nobody plans to remove it (owner, 2026-11-14). Which renderer fits depends on the world: sectors are fast and simple for rooms joined by portals; meshes can put anything anywhere.

## Model

- A world is a set of **objects** (0 .. 16383). An object is a triangle mesh with a position, a heading (yaw about the z axis), a light level (0 .. 255) and flags. The mesh is in the object's own coordinates; `M3D OBJPOS o,x,y,z[,yaw]` moves and turns it (a door is an object that turns about its hinge).
- **Things** (0 .. 1023) are billboards: a picture of a given width and height that always faces the viewer, with its bottom at `z`.
- Coordinates: x east, y north, z up; angles in degrees, 0 = +x, 90 = +y; to the right of the view direction is clockwise. A triangle is **counterclockwise seen from its front** (the normal `(b-a) x (c-a)` points to the viewer); one-sided objects do not draw or collide with the back. `M3D OBJECT o,16` (two sided) draws both sides.
- Pictures are `GFX GRAB` blocks (`M3D TEXTURE n,a$`, as for `W3D`); **`M3D TEXTURE LOAD n,file$[,PALETTE]`** (2026-11-20) makes picture n from a BMP file (window host; the console host has no palette and says so): the same as `GFX LOAD` onto the target layer, `GFX GRAB` of the picture and `M3D TEXTURE`, without touching the layer. The file name follows `GFX LOAD` (".bmp" is added when the last part has no extension; the policy and drivers apply); the colors are matched to the palette of the `GFX TARGET` layer (nearest entry, entry 0 stays transparent; palette entries with their own alpha count by their color only), with `PALETTE` the file's palette is installed in that layer first (an indexed file keeps its indices; this changes the colors of everything on the layer, and `M3D COLORMAP` should be called again). The size is that of the file, 1 .. 1024 either way. `gfxfile_make_picture()` in `gfxfile.c` does the work; tests: `gfxtest1`, `contest1`, `m3dtexhost.sh` (window host under Xvfb: the loaded picture renders byte for byte like the grabbed one). palette index 0 is see-through where the object is masked (flag 1) or translucent (flag 2) and always in things. A picture number with no picture draws that palette color flat.
- `M3D BOX o,x1,y1,z1,x2,y2,z2,tex[,faces]` adds the faces of a box (picture coordinates 1 texel = 1 unit, anchored to the object, so neighbouring boxes match; `faces` is a bit mask of the sides to build: 1 +x, 2 -x, 4 +y, 8 -y, 16 top, 32 bottom, default 63 = all, so a box can leave out a side that a quad with another picture covers: a house front with a door). `M3D VERTEX o,x,y,z[,u,v]` numbers vertices from 0 per object; `M3D FACE o,a,b,c,tex` and `M3D QUAD o,a,b,c,d,tex` add triangles; without `u,v` the picture coordinates follow the position by the direction of the face.
- Object flags: 1 masked, 2 translucent (mixed half and half, drawn last, far to near), 4 **passable** (no collision and no floor or ceiling), 8 **see-through** (shots, `USE` of walls and sight pass: glass, a railing), 16 two sided.

## Drawing

Every triangle is culled (back face, behind the viewer, off the screen), clipped against the near plane (2 units) and rasterized with a z buffer and perspective-correct picture coordinates; the light level of the object, the lamps (`M3D LAMP n,x,y,z,radius,amount[,dx,dy,dz,angle]`, up to 8, per pixel, brightening only; with a direction and a half angle in degrees the lamp is a **cone**: full on the axis, nothing at the edge, linear in the cosine of the angle to the axis, times the distance falloff; without them it shines all round) and the fog (`M3D FOG d`: dark at distance d) pick a row of the color map (`M3D COLORMAP` builds it from the palette). Order: the sky (`M3D SKY`, a picture around the viewer by angle), opaque and masked objects, things (far to near, depth tested), translucent objects (far to near). `M3D FAR d` skips what lies beyond d. Cost: about 1.6 ms for a test scene at 320 x 150 (`M3D VIEW x,y,w,h,2`).

## Collision, floors, rays

The player is a vertical capsule (`M3D PLAYER radius,height,eye,step`, default 14, 56, 46, 24), `M3D CAMERA x,y,z,yaw[,pitch]` puts the **feet**. `M3D MOVE forward,right` moves in small pieces, pushes the capsule out of the triangles it touches (spheres at the middle heights; everything lower than `step` above the feet is walked over), slides along an axis when blocked, refuses a floor more than `step` higher, refuses a ceiling lower than the player's height, and then lets the feet follow the floor (`M3D("FLOORZ")`, `M3D("FLOORAT",x,y,z)` = the highest surface at or below z, `("CEILAT",x,y,z)` the lowest above). `M3D LIFT h` raises the feet above the floor (a jump: steps up to `step` above the raised feet are taken). `M3D("HIT")`: 1 = something pushed, 2 = no movement at all.
Rays use the same triangles: `M3D("SHOOT",range)` (things and objects, the last shot is in `SHOTKIND` 0 / 1 object / 2 thing, `SHOTOBJ`, `SHOTDIST`, `SHOTX/Y/Z`), `M3D("USE",reach)` (the object in front, whatever its flags), `M3D("SEES",n)` (a thing's line of sight to the eye).

## Zones, walking things, the world document

- **Zones:** `M3D ZONE id,x1,y1,x2,y2,z1,z2[,tag]` names a box of space for the game (a room); `M3D("ZONE",x,y,z)` is the id of the first zone that contains the point (z within z1 - 2 .. z2), -1 if none, `M3D("ZONETAG",x,y,z)` its tag. The renderer does nothing with them. Put the zones of an upper floor and of a chair or table you can stand on *before* the zones below them. `M3D CLEAR` deletes them.
- **`M3D THINGMOVE n,dx,dy`** walks a thing like `M3D MOVE` walks the player (a body of radius 0.4 x width, at most 14, the player's step height; it follows the floor); `M3D("HIT")` tells whether a wall pushed it.
- **`M3D WORLD`** builds the world from the current JSON document (`JSON LOAD` first), replacing objects, things, lamps and zones; pictures and settings stay:
- **The ground: `M3D GROUND`, `M3D GROUNDFLAT`, `M3D TERRAIN`, `M3D("GROUND",x,y)`** (2026-11-20, roadmap item 95): a ground height function that lives in C (`m3d_ground()` in `m3d.c`, on the noise of `noise.c`, `docs/noise.md`) and a statement that fills an object with a grid of it. `M3D GROUND seed,scale,amp,octaves[,base[,gain[,lacunarity]]]` defines `height = base + amp * FBM(seed, x / scale, y / scale, octaves, gain, lacunarity)` (scale > 0; octaves 1 .. 16; base 0, gain 0.5, lacunarity 2 by default). `M3D GROUNDFLAT n,cx,cy,rx,ry,margin` (n = 0 .. 7) flattens the ground towards 0 round a box: the height is multiplied by `1 - w`, where `w` is 1 inside the box (half sizes `rx`, `ry`) and falls smoothly to 0 over `margin` units outside it (`(1-d)^2 (1+2d)`, d the distance in margins); margin 0 removes slot n. **`M3D TERRAIN o,x0,y0,nx,ny,cell,tex[,cells$[,skirt[,uvscale]]]`** adds to object `o` (made with `M3D OBJECT` first) a grid of `nx` x `ny` cells (1 .. 256) of `cell` units from `(x0,y0)`: `(nx+1)(ny+1)` vertices at the ground's height, two triangles a cell, counterclockwise seen from above (the same as `M3D QUAD o,b,b+1,b+nx+2,b+nx+1`). The picture of a cell is `tex` plus the code of its character in `cells$` (one character per cell, row after row from `y0` on, `nx` to a row; empty = `tex` everywhere; strings are bytes, so offsets 0 .. 255); `skirt` > 0 hangs a wall of that depth under the four edges (it hides the cracks between a coarse grid and its finer neighbour, for levels of detail); the picture coordinates are the position times `uvscale` (0.5 by default: 2 units a texel, absolute, so neighbouring grids match). `M3D("GROUND",x,y)` is the height of the function (0 when none is defined) *without* any object: the flat boxes are in it, trees and walls are not. `M3D CLEAR` and `M3D RESET` forget the function. A grid is a plain mesh: walkable (`M3D("FLOORAT")` follows its triangles, which are the function only at the grid points), solid, drawn by both renderers, kept by the hardware renderer's buffers. Tests: `m3dtest1` (ground values, counts, floor, pictures seen from above, errors), `contest1`. In `demos/1987.bas` a chunk of 9 x 9 cells is one `M3D TERRAIN` call (before: 100 `M3D VERTEX` and 81 `M3D QUAD` calls with 100 sine sums in BASIC; 130 chunks took 40 ticks, now 20).
- **Mountains and lakes in the ground function: `M3D MOUNTAINS`, `M3D LAKES`, `M3D GROUNDQUIET`** (2026-11-20, roadmap item 95). `M3D MOUNTAINS seed,scale,amp,octaves,lo,hi` adds `amp * t * RIDGED(seed, x / scale, y / scale, octaves)` to the height, where `t` is a smoothstep of a slow noise (`FBM` of 2 octaves at four times the scale, -1 .. 1) between `lo` and `hi` (-1 <= lo < hi <= 1): ridged noise has sharp crests, so ranges and peaks appear only where the slow noise is high (lo 0.05, hi 0.4 covers about 8 % of the plane with ground above 120); `amp` 0 removes the layer. `M3D LAKES seed,scale,depth,lo,hi` lowers the ground by `depth * t` where an `FBM` of 2 octaves at `scale` is between `lo` and `hi` (basins that the game fills with water); `depth` 0 removes it. `M3D GROUNDQUIET cx,cy,rx,ry,margin` keeps both out of a box and fades them in over `margin` (the hand-made area of a game); margin 0 removes it. The order in `m3d_ground()`: base + hills, + mountains, - lakes, then the flat boxes multiply. All of them reset with `M3D CLEAR`; `M3D TERRAIN` and `M3D("GROUND")` see them. `RIDGED(seed,x,y,octaves[,gain[,lacunarity]])` is the language function behind it (`docs/noise.md`). Tests: `m3dtest1` (the formula, removal, quiet box, errors), `noisetest1` / `vmtest1` (RIDGED golden values from the Python port).
- **The static world's ground: `M3D WORLDMAKE`, `WORLDOPEN`, `WORLDVIEW`, `WORLDWAIT`, `WORLDCLOSE`, `M3D("WORLDINFO")`, `M3D("WORLDCHUNK")`** (2026-11-21, owner: a world created once at new game, never decided during play): the ground of a world on disk (`world.[ch]`) is drawn by a quadtree of 8 x 8 cell tiles on the ground job machinery (mode 4), split and merged by the distance from the camera with nested grids and the `M3D MORPH` blend, so nothing pops; full description, numbers and tests in `docs/world-subsystem.md`.
- **The layers of the ground and the road network (2026-11-21, owner: "the order in which things are generated should be: meadows and fields first, then dirt roads, then hills, then tarred roads going across any terrain; lakes, mountains and decorations like trees and bales last"):** `roadnet.[ch]` (no SDL, pure) is the road network of the ground function: regions of `spacing` units each have a feature point (a kind: plain / meadow / field / forest, 14 / 28 / 20 / 38 %) and roads (`chance`) to the point of the west and the south neighbour, a part (`tarfrac`) tarred, all wandering sideways (`wdirt` / `wtar`) in steps of 50 units; the numbers are those of `demos/1987.bas` (`HASH(rx, ry, 1 / 2 / 3)` points, `60 + e` road, `70 + e` tarred, `NOISE(77, ...)` wander), so the game draws the roads where the ground expects them. **`M3D ROADNET spacing,chance,wdirt,tspacing,tchance,wtar`** (spacing 0 = no dirt tracks, tspacing 0 = no tarred roads; since 2026-11-21 the tarred roads are a network of their own: long roads between far apart region points, see the rings below), `M3D("ROADD",x,y)` / `("ROADT",x,y)` (distance to the nearest dirt / tarred road, 1e9 beyond 700), `M3D("KIND",x,y)`. `m3d_ground()` builds the height in the order of the generation, every layer adapting to the ones before it: (1) the basic ground (FBM) and the kinds; (2) dirt roads; (3) **hills** (`M3D HILLS`) fade out within 80 .. 280 of a dirt road and are a tenth on a field; (4) **tarred roads cut across any terrain**: within 240 of the road's middle (the road and its shoulder) the ground is the mean height of the base ground and hills along the road (7 places 150 apart), fading over 240 .. 520: banks and cuttings; (5) **lakes and mountains** keep away from every road (nothing within 120 of a dirt road or 300 of a tarred one, full strength from 300 / 700 on): a lake is cut in two by a road, a mountain's foot stops before it; (6) the flat boxes. Everything the roads do fades towards the quiet box. Cost: a ground sample near roads is about 10 times dearer (a few microseconds), far from them it is hardly dearer. Tests: `m3dtest1` (the road ends are the region points, the ground on a dirt road is the plain ground, on a tarred one neither drowned nor a mountain and flat across, a field has a tenth of the hills, mountains and lakes are everywhere without the network, `M3D CLEAR` forgets it), `contest1`.
- **The chunks morph too (2026-11-21, owner: "Fix the chunk-level hill popping -- geometry shouldn't change in front of the player"):** `M3D RING ... a,b` works for chunks (modes 1 .. 3) as for rings: every vertex keeps its height as made and as the grid of 3 times the cell has it (trees move with the ground under them: `jv_addtree`, `dz`) and `M3D MORPH x,y` blends them by the Chebyshev distance from the camera. **The levels are chosen so that a chunk only changes its level where it is wholly blended already** (the nearest point of the first chunk of the next level is at least `b` away): level 0 (cell 100, up to 2 chunks away) blends into the grid of 300 between 900 and 1800 units, level 1 (cell 300, up to 5 chunks) into the grid of 900 between 2700 and 4500; level 2 (one cell of 900) matches ring 2. So a level change shows nothing, and a chunk that comes closer grows its detail smoothly. **Cheaper:** `M3D MORPH` does nothing when the camera moved less than 8 units, and leaves an object alone whose rectangle lies wholly inside w = 0 or w = 1 and is so already (`obj_t.msat`, the rectangle `mx0 .. my1`); a ground job whose shaded picture cannot be made (no palette) keeps the cell's own picture. Test (`game1987test.sh` 11f7, play-back command `pop`): walking 300 steps of 5 units over hilly ground, the ground read at 40 places 700 .. 6400 units ahead changes by 0.2 .. 4 units from one step to the next (on the steep walls of the mountains up to 125 units per 5 units of walk, smoothly: the surface really is that different at the two detail levels there); `m3dtest1` +11.
- **Trees in the ground jobs, the morph of the rings, a bigger window (2026-11-21, owner: "do far trees and a bigger window, and also the geomorphing of the ring seams. Trees should not be placed on tarred roads. There is still a lot of popping everywhere, at least most of it appears to be asynchronous"):** (1) **a chunk's trees are part of its job**: `M3D RING` modes 2 (lathe trees as `TREEPROTO` of `demos/1987.bas`: trunk and crown of 8 sides, 64 .. 80 triangles) and 3 (cheap trees: a cone of 4 sides on a square trunk, 12 triangles), `M3D TREEPIC bark,leaf0,leaf1,leaf2`; the placement is `CHTREES` ported to C (up to 24 a chunk at hashed places in forest, ground between the water and a height of 70, 70 units apart, **not within 100 of a dirt track or 310 of a tarred road**, a hash for kind, turn and size); the trees are in the chunk's mesh (one object a chunk, solid); (2) **the dirt tracks are ribbons** in the chunk's mesh too (`RINGPIC ... dirt`, 110 wide, 3 columns, pieces of 50, heights from the mesh); (3) **the worker does the chunks before the rings** (the ground the player stands on first: the trees used to hang over missing ground while a ring was made: most of the popping that "seemed asynchronous"); (4) **`M3D MORPH x,y`** (every frame): a ring made with `M3D RING ... a,b` keeps for every vertex its height as made and as the coarser ring has it (also the ribbons and the skirts) and blends them by the vertex's Chebyshev distance from the camera, 0 up to `a`, 1 from `b` on: a hill rises or sinks continuously as the player comes or goes, and two rings meet without a step (the weights follow the camera, so making a ring again changes nothing you can see); (5) `M3D_MAXOBJECTS` is 28000. Tests: `m3dtest1` 1867 (trees: more triangles, cheap trees in steps of 12; dirt ribbons; the morph at a vertex, far away and halfway; clean under ASan / UBSan / TSan).
- **Rings of ground made on a worker thread: `M3D RING`, `RINGPIC`, `RINGMORPH`, `POLL`, `RINGWAIT` (2026-11-21, owner: "go ahead with the rings ... use precomputation to avoid popping ... chunk creation should be asynchronous -- implement multithreading if it needs to be"):** the ground meshes are made in C by **one worker thread** (`pthread`, `m3d.c`; the ground function and the road network are pure, `roadnet.c` keeps its cache per thread; the job gets a copy of the ground function, the program thread never waits). **`M3D RING o,x0,y0,n,cell,skirt,mode,hx0,hy0,hn`** queues a job that replaces the mesh of the existing object `o` (make it with `M3D OBJECT` first; the old mesh stays until the new one is taken): a grid of `n` x `n` cells of `cell` units from (`x0`, `y0`), a hole of `hn` x `hn` cells at (`hx0`, `hy0`) where a finer grid lies (the cells of the hole are left out), a skirt under the outer and the hole edges, the slope shading of `M3D SUN` (the shaded pictures are made when the result is taken), and the picture of each cell by a rule in C set by **`M3D RINGPIC water,rock,grass,tar,tarfar,mud,meadow,field,forest,level,rockh`**: **mode 0** (a ring): water below `level` - 3, rock above `rockh` or steeper than 0.9, else grass; **mode 1** (a chunk round the player): the rules of `FN OCELL` of `demos/1987.bas` (the hand-made area keeps the noise pictures grass / grass + 1 / grass + 2 and the mud of the wheat field; outside: rock above `rockh` or steeper than 45 over 100 units, mud below `level` + 1.5, else the kind of ground of the road network: meadow / field / forest, the plain's noise pictures). (`M3D RINGMORPH` of the first version, a weight fixed when a ring was made, was replaced the same day by `M3D MORPH`, see above.) **Tarred roads** of the network (`M3D ROADNET`) are **ribbons** in the mesh of every job (not inside the quiet box): 5 columns of vertices across (440 wide, a quarter of the cell wide in the far rings so that they are seen), a piece every 100 units in a chunk or every cell in a ring, the heights **taken from the mesh itself** (`job_meshh()`) plus 3 .. (3 + 2 % of the cell), so a coarse mesh never pokes through the road (before, the ribbons took the ground function's height and showed holes where the mesh bulged); the chunk that holds the start of a piece makes it, the picture is `tar` (`tarfar` in the rings of 2700 and more). **Taking the results:** `M3D POLL` takes finished jobs: a chunk (mode 1) at once, the rings (mode 0) **only when none of them is queued or working any more** (they change together: no gap or overlap between two rings); `M3D RINGWAIT` waits for all jobs and takes them (the start of the game and a `goto` do that: everything is precomputed); `M3D("RINGBUSY")` counts the jobs not taken; a job for an object that has not started yet is replaced by a newer one (the latest wins); at most 160 jobs wait; `M3D CLEAR` / `RESET` forget them. Worker thread: `M3D("DRAWN")` and everything else is unchanged; `m3dtest1` (+40: counts, hole, skirt, a job for an undefined object, the morph on the edge and at a coarse vertex, ribbons: more triangles, the ribbon above the ground, none without a tar picture; clean under ASan / UBSan and ThreadSanitizer). **`M3D FOG d,haze,start`**: nothing before `start`, quadratic from there to `d` (at most 92 %); **`M3D("QUIET",x,y)`** is 0 in the quiet box and 1 outside. A link needs `-pthread` only on a glibc older than 2.34.
- **Fog of a haze color, a far land (the far tiles and the middle ring were replaced by the rings the same day), real mountains and lakes (2026-11-21, owner: "make the lakes real size ... think of a way to make real mountains. It's no problem if they appear as walls up close ... the viewing distance is extremely short and players see stuff popping in"):** (1) **`M3D FOG d[,haze]`**: without `haze` the fog darkens with the distance as before; with a palette index (1 .. 255) things fade *to that color*: `f = min(1, z / d)^2` (gentle near, strong far), at most **92 %** (`M3D_HAZEMAX`: far things keep a trace of their own color). The software renderer has a table `haze[16][256]` (palette color nearest to color i mixed with the haze color; made when first needed, again when the palette changes; `m3d_nearest_rgb()`), the hardware renderer mixes in the shader (`u_haze`). The sky is not fogged (choose the horizon's color as the haze color). Tests: `m3dtest1` (exact values for q 0.5, 0.77, beyond, errors), `m3dgltest1` ("haze" and a far, very high wall compared with the software picture). (2) **`M3D HILLS`** is a second ridged layer next to `M3D MOUNTAINS` (`ground_t.mnt[2]`), and both take two more arguments `r0,r1`: the layer fades in between these distances from the origin (so mountains can keep away from the start). (3) **Holes in a terrain grid:** the character 255 in the cell string of `M3D TERRAIN` leaves out that cell (and its piece of the skirt), so a coarse tile can leave room for the finer grids inside it. Heights of 40000 units and distances of 40000 are no problem (`m3dtest1`).
- **Walking on hills (2026-11-21, owner: "they should be passable by foot and bike ... some games move the player upwards until they're not colliding with the terrain"):** (1) in the sideways push of a body (`push_out()` in `m3d.c`) a triangle whose normal is within about 72 degrees of vertical (`|n.z| >= M3D_WALKABLE_NZ` 0.3) no longer counts as a wall: the floor under the body and the step height decide whether a slope can be climbed (a piece of a walk is at most `radius / 2` = 7 units, so a rise of 24 per piece allows 72 degrees); before, any hillside triangle that came within the body's sphere pushed it back, so slopes of 40 degrees and more stopped a walker (ceilings are still checked by `ceil_at`). (2) **With a ground function (`M3D GROUND`) a body cannot be lost** (`body_floor()`, `unbury()`): when there is no floor mesh under it (not built yet) the ground function is the floor; when no floor is found below, the first surface above it is (the body is lifted out of the ground); a body more than 60 units below the ground function (the mesh was made again under it, a teleport before the chunk existed) is lifted onto the first surface above it, or onto the function. Without a ground function nothing changes (a body over a hole still has no floor and stays where it is). Tests: `m3dtest1` +40 (a 60 degree ramp is climbed, a wall still stops a body, the ground function as the floor, buried body lifted, no change without a ground function; clean under ASan / UBSan).
- **What the floor is made of: `M3D("FLOORTEX",x,y,z)` and `M3D("FLOOROBJ",x,y,z)`** (2026-11-21, owner: "Our current method by height only is quite imprecise ... a function that returns the texture ID of the highest triangle below the player position"; a 1 x 1 `M3D MINIMAP` cannot do it: it samples the ground *function*, not the meshes, and draws onto a layer): they find the same surface as `M3D("FLOORAT",x,y,z)` (the highest solid triangle at or below `z`; passable objects, flag 4, are no floor, so the water planes and decorations are skipped) and return its **picture number** (`FLOORTEX`) or its **object number** (`FLOOROBJ`); -1 when there is nothing. For a cell of a shaded terrain (`M3D SUN`) the number of the cell's own picture is returned, not that of the darker copy. Roads, mud, rock and brick in `1987` are pictures (`OCELL`: 320 mud, 324 rock, kind pictures; 304 road; 326 brick), so the picture says what the ground is. Cost: one ray as for `FLOORAT`. Tests: `m3dtest1` (+19: highest of two, below the block, nothing, passable, shaded cell), `contest1`.
- **Height map: `M3D MINIMAP sx,sy,w,h,wx,wy,span[,water]`** (2026-11-21, owner: "Yes, add the minimap statement"): there is no stored height map (the ground is the function `m3d_ground()`), so this samples it: a picture of `w` x `h` pixels (1 .. 512 each) is drawn onto the `GFX TARGET` layer at `sx`, `sy`, showing the square of `span` world units across round the centre (`wx`, `wy`); north (larger y) is up, pixels are square (the height covers `h * span / w` units). Colors by height: below `water` (optional, default none) blue, darker the deeper (up to 40); then green (0), light green (40), brown (90), grey (150), white (230 and up), shaded by the slope against the sun (`M3D SUN`, else a default sun from the south-west; level ground is not changed; lit slopes up to 1.2 times, shadowed slopes down to 0.45), every color the nearest entry of the target layer's palette (index 0 never). It shows the function including the flat boxes, mountains, lakes and quiet box, not trees or buildings. Cost: 5 ground samples a pixel (two 300 x 300 maps about 0.9 s under Xvfb, so draw it once or rarely, not every frame; a layer or a picture can hold it). The console host checks the numbers and draws nothing. `m3d_minimap()` in `m3d.c` computes the indices (tests: `m3dtest1` +22, `contest1`); the host (`host_m3d_op`) puts them on the layer. Seen under Xvfb: 1987's ground (quiet area, mountains, lakes).
- **Shaded terrain: `M3D SUN dx,dy,dz[,ambient[,steps[,stride]]]`** (2026-11-21, owner: "Yes, do the baked version in M3D TERRAIN"; the renderers have no normals and one light value per object, so the slope shading is baked into the *pictures*): the direction towards the sun (any length, `dz` > 0; all three 0 = off); `ambient` (0 .. 1, default 0.5) is the brightness of the darkest step, `steps` (2 .. 8, default 4) the number of brightness steps counting the unshaded one, `stride` (1 .. 1023, default 100) the picture number step. `M3D TERRAIN` then takes for every cell the normal of its slope (from the four corner heights: `(-dz/dx, -dz/dy, 1)`), `lam = max(0, n.L) / L.z` (1 on level ground, so level ground is never changed; slopes facing the sun are not brightened, there is no color brighter than the picture itself), the step `k = round((1 - lam) (steps - 1))` and uses the picture `t + k * stride` instead of `t`. That picture is made by the engine the first time it is needed from the cell's picture `t`: every palette index is replaced by the palette color nearest to it darkened to `1 - k / (steps - 1) (1 - ambient)` (the same search as the software color map, `m3d_shade_index()`; index 0 stays); a flat color below 256 without a picture becomes a picture of one texel; a picture number above 1023 or a flat color above 255 stays unshaded. The skirt takes its cell's picture. The shaded pictures are made again in place when the palette (`M3D COLORMAP`) or the sun changes (a step that is gone is deleted), so **set the palette first and define the sun before building terrain**; with no palette yet (console host, before `M3D COLORMAP`) nothing is shaded. Both renderers draw them (they are ordinary index pictures; the hardware one uploads them like any picture). Keep the numbers `t + k * stride` free for the engine: it fills an empty number and uses a picture that is already there. `M3D CLEAR` forgets the sun (the pictures stay), `M3D RESET` deletes all. - **Instances: `M3D INSTANCE`, `M3D OBJSCALE`, `M3D OBJFREE`** (2026-11-20, roadmap item 95): many objects of one shape without a copy of the mesh. `M3D INSTANCE o,src[,x,y,z[,yaw[,scale]]]` makes object `o` (made again if it exists) **share the mesh of object `src`** (it must be defined; not itself), with its own place, heading and size (`scale` > 0, default 1: vertices and heights are multiplied, the picture coordinates are not). ## Renderer interface

The module is split into the world model (`m3d.c`: objects, things, lamps, camera, collision, rays, the operations and queries) and a renderer behind the interface `m3drend_t` in `m3dpriv.h` (`create`, `destroy`, `resize`, `palette`, `render`). The model owns the palette and everything that behavior depends on, so a query answers the same whatever draws. The software rasterizer is `m3dsoft.c` (`m3d_soft_renderer`; its color map, translucency table, bitmap and depth buffer are its own). A second backend (OpenGL 2, 32 bit ARGB output) is planned; see `SESSION.md`.

### Choosing the renderer (`M3D SOFTWARE`, `M3D HARDWARE`)

`M3D SOFTWARE` switches to the software renderer (always possible, the default). `M3D HARDWARE` switches to the OpenGL 2 renderer; where there is none it is the error "Hardware renderer not available". `M3D("RENDERER")` is 0 or 1 for the one in use, `M3D("HWAVAIL")` is 1 when `M3D HARDWARE` can succeed (a program asks before it switches). **`M3D HIDE` (2026-11-21):** the hardware renderer's picture lives in a 32 bit layer of its own that is drawn just *below the graphics layer that was the target when it was put* (so the HUD stays in front). A program that flips between two graphics layers (`W3K_SHOW`: layers 0 and 3) and shows a 2D screen after 3D frames (title, loading screen) had the old 3D picture over the layer 0 buffer on every other frame: the game flickered through the title and the progress screen. `M3D HIDE` (`sdlscr_3d_hide()` in the window host, nothing in the model or the console host) removes the layer until the next `M3D RENDER` and makes the renderer forget everything it kept (`m3d_invalidate()`: the kept meshes are built again, the palette is made again; the same effect as the 3D settings dialog, which was found to cure the glitches seen after the title); `demos/1987.bas` calls it at the start of the title and in `LOADING`. **Full-scene antialiasing (2026-11-21):** `M3D MSAA n` (0 off, 2 .. 16 samples) makes the hardware renderer draw the frame into multisampled renderbuffers (colour and depth, `glRenderbufferStorageMultisample`) and resolve it into the frame buffer object with `glBlitFramebuffer` before the read back; `M3D("MSAAMAX")` is the most samples the driver offers (found by the probe in `glload.c` from `GL_MAX_SAMPLES`; 0 when the two functions are missing, so there is none; `M3D("MSAA")` is the number in use, 0 with the software renderer). A request above the maximum is cut down; a driver that refuses the buffers draws without. Only geometry edges are smoothed (the pictures are sampled nearest). The setting survives `M3D RESET` and a switch of renderer. `prefs3d.lib` has an **Antialiasing** row (Off, 2X, 4X, ...; shown for mesh programs when `M3D("MSAAMAX")` is at least 2; the default is 4X or the maximum; the eighth value line of `3dprefs.cfg`) that `W3K_SETAA` hands to `M3D MSAA`. Tests: `m3dgltest1` (the edges change, a few percent of the pixels, and off gives the first picture back), `m3dtest1` (the statement and the queries). `M3D RESET` keeps the choice; the palette and the view carry over a switch. The model (`m3d.c`) does not know OpenGL: the window host registers the hardware renderer with `m3d_set_hardware()` (`m3dgl.[ch]`: `m3d_gl_renderer()`); the console host registers none. Switching builds the new renderer's state first, so nothing changes when that fails. `m3dtest1` tests the switching with a stand-in renderer.

**Status: the renderer exists** (`m3dgl.c`, step 4); the choice in the 3D preferences and the default (hardware when `M3D("HWAVAIL")`) exist since step 5: `W3K_MESH` in `w3dkit.lib` selects the hardware renderer when it is available, `prefs3d.lib` has a **Renderer** row (Software / Hardware, saved as the sixth line of `local:3dprefs.cfg`, shown only for programs that use `W3K_MESH` when hardware is available).

### The OpenGL binding (`glload.[ch]`)

No GL library is linked. SDL opens the system's library (`SDL_GL_LoadLibrary`) and hands out addresses (`SDL_GL_GetProcAddress`); `glload_bind()` keeps the 60 functions the renderer needs (GL 1.1 drawing and textures, buffers, GLSL shaders, framebuffer objects under the core, ARB or EXT names) in a `glapi_t` while a context is current; one missing function means "no OpenGL 2". `glload_probe()` runs once in the screen thread when the window opens: it makes a hidden window and context, binds, reads `GL_VERSION` (>= 2.0), destroys them again and gives the current context back to the SDL renderer; the result is an atomic state (`glload_state()`, `glload_info()` with the version, the renderer's name and the reason for a "no"). `ENGINE1999_NOGL=1` skips the probe (answer: no). `gltest1` (in `make check`; skipped without a display or without OpenGL 2, `GLTEST_REQUIRE=1` makes a skip a failure) checks the probe, the binding and real drawing: a shader fills a framebuffer object and `glReadPixels` returns it (seen with an NVIDIA driver and with Mesa's llvmpipe under Xvfb).

### Pictures: palette bitmap or ARGB

A renderer says in `m3drend_t.argb` what its picture is. The software renderer makes a palette bitmap (`m3d_render()`, copied into the target layer by `sdlscr_gfx_putbuf()`); a hardware renderer makes 32 bit ARGB (`m3d_render32()`; `m3d_render()` returns 0 for it and the other way round, `m3d_is_argb()` tells which) and the window host puts it into the 32 bit layer, `sdlscr_3d_put()` (`docs/graphics-subsystem.md`). The colormap and the translucency table are software only; a hardware renderer lights and blends in true color.

### The hardware renderer (`m3dgl.c`)

**Where it runs:** on the thread that calls `M3D RENDER` (the program thread), with an OpenGL context of its own on a hidden window (made at `M3D HARDWARE`, deleted when the renderer is left or the module freed); the context is made current again at each frame if another thread had it. The screen thread, its SDL renderer and the probe are not involved, there is no hand-over of a context between threads. If the program thread ever changed while the context is current on the old one, switching would fail (not seen: the VM runs on one thread). The picture goes into the 32 bit layer by the host, `sdlscr_3d_put()`.

**What it draws, in this order** (as the software renderer): the sky (a fullscreen triangle whose shader looks the picture up per pixel from the view direction exactly as `draw_sky_bg()` does, or a flat clear color), the opaque objects (**kept meshes since 2026-11-15**: every object's triangles sit in a vertex buffer of their own in the object's own coordinates, grouped by picture; per frame the CPU only tests the object's bounding sphere and draws it with its place, heading and light as uniforms, one draw call per picture; back faces are culled by the hardware (`GL_CULL_FACE`, front faces wind clockwise because the picture is rendered upside down) for objects that are not two sided; the vertex shader moves the object into the world, makes the view and the projection with the same pinhole camera, the near plane 2 and a far plane from `M3D FAR`; the picture is rendered upside down so that the first row read back is the top one), the things (a rectangle facing the viewer at the depth of the thing's middle, back to front, no depth write), the translucent objects (back to front, mixed half and half). **Pictures** are uploaded once as 8 bit index textures (`GL_LUMINANCE`, nearest, repeating; again when `tex_t.gen` changed), the palette is a 256 x 1 texture and the fragment shader looks the index up in it (index 0 of a masked picture is discarded); a flat-color face uses an identity texture. **Light:** the object's light plus the lamps' light at the point (`amount * (1 - distance / radius)`), times the fog (`1 - depth / fog`), as in the software renderer, but as a smooth factor on the true color instead of 32 steps and the nearest palette color. **Palette:** the host hands the target layer's palette over before each frame (`M3D COLORMAP` is not needed in hardware mode; a palette fade shows at once).

**Tests:** `m3dgltest1` (in `make check`, skipped without display or OpenGL 2) draws ten scenes with both renderers (plain, light, fog, lamp, flat and picture sky, masked, translucent, things, camera) and compares them pixel by pixel on a ramp palette: at most a few percent of the pixels may differ (the measured mean difference is below 1.2 of 255; the differences are edge pixels); it also checks that a changed view and a changed picture reach the hardware renderer. `m3dglhost.sh` (in `make hosttest`) runs the real window host under Xvfb: a typed-in program draws a scene with the software renderer, switches with `M3D HARDWARE`, draws again and switches back, and the screenshots are compared (the two pictures were identical byte for byte).

**Speed (measured 2026-11-14 under Xvfb, where OpenGL is Mesa's CPU renderer llvmpipe, so the hardware numbers say little about a real GPU):** Deqq's House II at 640 x 264, 120 frames turning in place at four places: software 2.4 .. 4.3 ms per frame (150 .. 2260 triangles drawn), hardware 4.3 .. 13 ms (320 .. 3240 submitted). **On the owner's machine (NVIDIA GT 710, 2026-11-14) the hardware renderer is faster:** software 2.2 .. 4.3 ms per frame, hardware 1.7 .. 2.1 ms (about 2 times, and nearly independent of the scene: the readback and upload dominate, not the triangles). **Scale 1 on the owner's GT 710 (2026-11-14):** hardware 2.2 .. 2.9 ms per frame at 640 x 264 (1.8 .. 1.9 ms at 320 x 132), software 7.2 .. 14.3 ms (2.2 .. 4.2 ms at 320 x 132): at the full size hardware is 3 to 5 times faster, and software at 14 ms is near the 16.7 ms frame budget. **Scale 1 (640 x 264 instead of 320 x 132), Xvfb / llvmpipe:** software 7.1 .. 14 ms per frame (3.5 times slower), hardware 8.3 .. 10 ms (CPU-emulated GL, so not meaningful); the real GPU's numbers: see `m3dbench.sh` (it now measures both scales). **The 3D preferences have the render size option (320 x 132 or 640 x 264; default 640 x 264 with hardware).**

**`sh m3dbench.sh` repeats the measurement on any machine** (it opens the window; type `LOAD "demos/deqq2"` and `RUN`; the program `BENCH` in `deqq2.bas` runs when the environment variable `DEQQ2_BENCH` names an output file). Per frame the hardware path collects the triangles on the CPU, sorts them, uploads and reads the picture back (`glReadPixels`), so on a fast machine it is not automatically quicker than the software renderer; not measured on a real GPU.

**Kept meshes (2026-11-15, owner: "implement keeping the graphics buffers of unchanged objects, by implementing the changed-flag per object in m3d.c and kept buffers in m3dgl.c"):** `obj_t.gen` (m3dpriv.h) is the **generation of an object's mesh**: a new number from a global counter whenever a vertex or a triangle is added or the object is made again (`M3D OBJECT`); moving or turning (`M3D OBJPOS`), the light, the flags and showing / hiding leave it alone (the old `dirty` flag stays what it was: world coordinates and bounds are made again, for the software renderer, the collision and the shots). `m3d_t.presepoch` counts the times a picture number got or lost its picture (`M3D TEXTURE`, `M3D RESET`). In `m3dgl.c` every object has a `gobj_t` (`gl_t.gobjs`, one per object number, allocated at the first frame): its buffer, the `gen` and `presepoch` it was built for and the list of picture ranges; `draw_gobj()` builds the buffer (`build_gobj()`: texels in the buffer, the picture's size is the uniform `u_texsz`, so a picture that is replaced by one of another size needs no new mesh; flat colors use the identity picture) when `gen` or `presepoch` differs and draws it, so **an unchanged object costs no CPU work per frame but its bounding test and a few draw calls, and no upload**; the billboards (things) still go through the small stream buffer. `M3D("DRAWN")` is not counted while drawing any more (the hardware culls): `m3drend_t.drawn` counts it when asked, from the camera of the last frame and the objects as they are then (same numbers as the software renderer: the tests compare them). `m3d_gl_built()` tells how many meshes were built (for tests: `m3dgltest1` checks that a second frame, a moved, turned, dimmed object builds nothing, a changed object builds one, a new picture number builds all). **What it costs:** more draw calls (one per object and picture instead of one per picture: the Bug Hunt style worlds with some 700 objects in view give a thousand or so), a meshes' memory in the graphics card (about 20 bytes per vertex), and objects that change every frame (John's body, the drone beams) are built again every frame as before. **Not measured on a real GPU** (Xvfb / llvmpipe: Mesa's CPU renderer: 35 .. 38 ms a frame before and 34 ms after in 1987, which says only that nothing got worse there); the owner's GT 710 is the place to look (`DEQQ2_BENCH` / `m3dbench.sh`).

**Culling counts, small objects, nearest first (2026-11-22, owner: "hide objects not seen or obscured ... could further reduce triangle costs"):** what was already there: both renderers skip an object whose bounding sphere is behind the viewer, beyond `M3D FAR` or outside the sides of the view, and single triangles that face away, lie behind the viewer or off the screen. New: **`M3D("CULL", k)`** counts the last frame (0 objects asked, 1 drawn, 2 skipped behind the viewer or beyond FAR, 3 skipped outside the sides, 4 skipped as too small, 5 skipped as hidden (always 0: there is no occlusion test yet), 6 triangles of the drawn objects; the hardware renderer counts them too) next to `M3D("DRAWN")`; **`M3D CULL smallpx[, sort]`** (default `1, 1`): an object whose bounding sphere is under `smallpx` pixels (and that does not reach the near plane) is not drawn, 0 turns it off; `sort` 1 draws the opaque objects of the software renderer **nearest first** (by the distance of the sphere's middle, ties by object number), so the depth buffer rejects hidden pixels before they are textured, 0 keeps the order of the object numbers. The picture is the same unless surfaces lie exactly on each other (then the nearer object wins, not the one with the higher number); translucent objects and things are drawn as before. **Measured** (`m3dtest1`, software, 640 x 264): 359 boxes behind a wall, added far ones first (the worst order): 14 ms a frame nearest first, 25 .. 27 ms in object order, the same picture. In the village of `tools/house3d.bas` (street view, 55 objects asked) 47 were drawn, 8 skipped outside the sides, none as too small; their triangles 11,100 of which 6,200 were rasterized (the rest facing away or off the screen). Not done: an occlusion test against a coarse depth buffer, visibility by room inside a house (the village's levels of detail in `tools/house3d.bas` do the coarse part).

**Not done / differences:** no clipping of the object list by a spatial structure; kept meshes of objects that were cleared stay in the graphics memory until the object number is used again; things stay in the stream. The three differences of the first version are gone (2026-11-14): `M3D("DRAWN")` counts the same triangles as the software renderer (what is left after clipping at the near plane; things are not counted by either), index 0 of a plain picture and a missing sky (no color, no picture) are see-through (the picture's alpha is 0 there and `sdlscr_3d_put()` leaves such pixels transparent, so the layers below show, as with software; ARGB renderers must set the alpha: 0 = transparent, anything else = opaque). The light is smooth, so hardware pictures have no banding.

**Window glass, the translucent-object bug and palette alpha (2026-11-14, owner: the west front had a gap above the door and the windows were bare holes; then "use a tinted texture with an alpha channel (from the palette) for the glass, plain color").**
- **Bug (both renderers):** the list of translucent objects and the list of things shared the scratch arrays `m3d_t.order` / `odist`; the things were drawn *between* collecting and drawing the translucent objects, so with any thing in the world the translucent objects were skipped or the wrong ones drawn (the 28 glass panes of Deqq's House II, which has 69 things, vanished). The things now use the upper part of the arrays (`M3D_MAXOBJECTS` on); `m3dtest1` has a case (it fails without the fix).
- **Palette alpha:** in a *translucent* object (flag 2) a texel whose palette entry has an alpha of its own (`GFX PALETTE n,i,RGB(r,g,b,a)`, a < 255) is mixed with that alpha (a = 0: nothing is drawn there); entries with alpha 255 mix half and half as before, opaque and masked objects ignore the palette alpha. Software: a table per alpha level (alpha / 8, 1 .. 31, `alpha_blend()` in `m3dsoft.c`, made when first needed, about 50 ms, thrown away with a palette change); hardware: the palette texture carries the alpha and the fragment shader takes it for translucent objects. `m3dtest1` (exact values 75 = 50 * 3/4 + 150 / 4, alpha 0) and `m3dgltest1` ("palette alpha", both renderers compared). A picture number with no picture draws the palette color of that number flat, so **a plain tinted glass needs no picture** (give the panes an unused picture number and define that palette entry with an alpha). The glass of Deqq's House II does *not* use this: its panes (objects 1058 .. 1085, flags 10, thin boxes in the window holes, one on each side of the wall) use picture number 11, which is the **sky picture**, so the glass shows clouds (an accident of the numbering that the owner liked; `docs/deqq2.md` §4.4). The palette alpha is tested but no game uses it yet.
- The wall above the west kitchen door (x 172 .. 180, y 520 .. 584, z 100 .. 300) was missing from object 1 and is closed.

**Cone lamps (2026-11-14, owner: street lamps that shine down at an angle).** `M3D LAMP n,x,y,z,radius,amount[,dx,dy,dz,angle]`: with a direction (any length but not 0) and a half angle (1 .. 179 degrees) the lamp is a cone: the light at a point is `amount * (1 - distance / radius) * spot`, `spot = (cos(angle to the axis) - cos(half angle)) / (1 - cos(half angle))` clamped to 0 .. 1, so it is full on the axis and zero at the edge of the cone; without direction and angle the lamp shines all round as before (one lamp keeps one mode: setting it again replaces it). Software: the per-pixel lamp loop of `m3dsoft.c`; hardware: a second uniform array `u_lampd` (xyz = the axis, w = the cosine, -2 = no cone) in the fragment shader of `m3dgl.c`; `lamp_t` got `dx, dy, dz, cc, spot`. Tests: `m3dtest1` (on the axis lit, 76 degrees off the axis dark, aimed away dark, the error cases), `m3dgltest1` ("spot lamp", both renderers compared). **A fix that came with it:** `GFX_MAXARGS` was 8 although `M3D BOX` has 9 arguments, so the VM wrote one `double` past its argument array at every `M3D BOX`; it is 12 now. Cost and use: `docs/deqq2.md` §11.1 (the game gives its spare lamp slots to the nearest street lamps every 0.1 s; software rendering: a lamp costs about 2 ms a frame at 640 x 264 in a street, 0.5 ms at 320 x 132; each triangle only carries the lamps whose reach touches its bounding box, `tri_t.lampmask`; outside a cone is found without a square root).

**The software rasteriser's span kernel (2026-11-21, owner: "Start with the SIMD work"):** `raster()` in `m3dsoft.c` draws a row four pixels at a time: `span4()` computes for four neighbours the depth `z = 1 / iz`, the depth-buffer and far tests, the texel coordinates `floor( u / z )`, `floor( v / z )` and (without lamps) the fog / haze step and the light level, all with GCC's **vector extensions** (`v4d`: four doubles, one AVX register or two SSE2 / NEON ones; no intrinsics, so the portable kit builds as it is; `-Wpsabi` is silenced for the static inline helpers). A scalar twin (`span4_scalar`, selected with `ENGINE1999_NOSIMD=1` or `m3d_soft_set_simd( 0 )`) computes **the same bits** (the file has `fp-contract=off`; the pixel's plane values are `B + gx * ( x + 0.5 )` per pixel instead of a running sum, which also removes the drift); `m3dtest1` renders hazed, fogged, lit, translucent scenes both ways and compares every byte, and the pictures equal those of the code before the change. Also: textures whose size is a power of two wrap with a mask instead of two integer divisions per pixel (the larger part of the gain). Measured (this machine: Sandy Bridge, AVX without AVX2 / FMA; terrain with a 16 x 16 picture, 640 x 264, fog): 4.0 ms -> 2.65 ms a frame (haze 4.76 -> 2.86; the SIMD part alone about 0.9 ms of that; plain x86-64 build 5.0 -> 4.4 ms; lamps 7.5 -> 6.0). **Not vectorised:** the lamp light per pixel (scalar, with square roots), the translucent mixing, the texel gather (no gather before AVX2), the triangle setup, `draw_object` (vertex transform, clipping), `rnet_near`.

**SIMD, second round (2026-11-21, owner: "Vectorize the lamp light next, then the other stuff from your 'not vectorized' list"):** (1) **the lamp light** is in the span kernel now (`span4()`: distance, cone test, cone factor and the sum over the lamps that reach the triangle, four pixels at a time; the float square root is `sqrtps` through `sqrtf4()`, the same value as `sqrtf( (float) d2 )`; `lamp_add1()` is the scalar twin); the divisions by the lamp's radius, by `1 - cos( angle )`, by the fog distance and by `fog - start` became multiplications with the reciprocal made once per triangle (on this machine a 4 wide division costs about as much as 40 multiplications, and with lamps three of them were left per pixel); the pictures stay byte-identical to the code of the day before in the benchmark scenes (a one-step difference in a light level at a rounding edge is possible in principle). Benchmark (same scene, 640 x 264): lamps 7.7 -> 4.05 ms a frame, haze + lamps 7.9 -> 4.8, fog 4.7 -> 2.7. (2) **`rnet_near()`** (`roadnet.c`, the ground function's road test) examines the steps of a road four at a time (`ENGINE1999_NOSIMD` / `rnet_set_simd()` for the scalar twin; the square root and the choice of the first nearest step are done only for a step that can beat the best so far, so the result is the scalar loop's): 1087 -> 807 ns a call; the rest is the cache lookups of 18 regions a call. `roadnet.c` has `fp-contract=off` now (the same numbers on every machine). Tests: `m3dtest1` 1958 (+1: 20000 places, both loops, equal bits). **Looked at and left alone, with the reason:** the translucent mixing and the texel fetch are table look-ups (`blend[ behind * 256 + front ]`, `col[ u * h + v ]`: gathers, which this CPU and the portable baseline do not have; scalar loads are what they cost anyway); triangle setup and `draw_object` are about 4 % of the instructions of a 7000 triangle frame (callgrind), spread over many small steps with a division by the triangle's area each: not worth a rewrite into structure-of-arrays; the VM is an interpreter (branches on every instruction), not a data-parallel loop: its gains come from fused instructions (`docs/compiler-and-vm.md`), not from vectors. Also found: one `M3D COLORMAP` / palette change costs about 72 million instructions (`m3d_shade_index()` searches the palette for every shade of every color): a palette fade every frame would be expensive; not changed.

**Portability of the vector code (2026-11-21):** `vecext.h` decides at compile time whether the vector code is built: clang 5+ and GCC 9+ (`__builtin_convertvector`); with an older GCC (Debian 10 / Ubuntu 18.04 and before), another compiler or `-DE99_NOVEC` only the scalar twins are compiled (same pictures bit for bit, about 1.8 times slower with lamps / haze: 7.4 ms against 4.1 ms in the benchmark). The "no fused multiply-add" and "no `-Wpsabi` warning" settings are macros there (`E99_NO_CONTRACT`, `E99_NO_PSABI`) that expand to the pragma of the compiler in use (`#pragma GCC optimize` is ignored by clang, which has `clang fp contract(off)`). Checked with GCC 12 and clang 14, `-O2` and `-O3 -march=native`, with `-Wall -Werror`: the same benchmark picture from all four builds and the fallback, and `m3dtest1` (which compares the two paths) passes with clang. **Not tried:** an FMA-capable CPU with `-march=native` (contraction is switched off, so it should give the same bits), non-x86 targets (NEON would take the same code), old GCC itself (only the `-DE99_NOVEC` build was tested).

### Palette log (`ENGINE1999_PALLOG`, 2026-11-22)

`ENGINE1999_PALLOG=file engine1999` appends a line to the file when the 3D renderer is given its palette: at `M3D COLORMAP`, at each of the first 12 `M3D RENDER` calls, and at each render where entry 249 of the target layer (the one the renderer takes its palette from) changed or a target layer is met for the first time. A line: the monotonic time (seconds, modulo 100000), `colormap` / `render`, the target layer, `hardware` / `software`, an FNV checksum of the target palette, then `L0`, `L3`, `L4` and the target's entries 248 .. 251 as ARGB hex. Made to find the cause of the green nose and ears of John in `demos/1987.bas` (they use the palette entry 249, `SK2`). Seen in a run under Xvfb: the target alternates between layers 3 and 0 every frame (the double buffer), both palettes equal; layer 4 (the sprite layer) holds the engine's start palette until the loading screen copies the game's palette into it.
