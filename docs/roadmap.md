# Roadmap — what is still to do

The list of open work, so that nothing is forgotten. `[ ]` = open, `[x]` = done (moved here when finished, then the entry can be
dropped). **Status of what already works** is in `SESSION.md` (state, tests, design decisions taken); this file is only about
what is **not** done. Items marked *needs design* wait for a language decision by the project owner before they can be implemented.
Order = suggested order, not a commitment.

language or design decision of the owner first. The ratings are my suggestion, not a commitment; the sections below hold the details. Keep this table in step with

## 14. A terminal emulator screen and a Claude screen *(owner's idea, 2026-11-01; nothing decided or started)*

The idea: a text screen of the Engine that is a terminal emulator, and a text screen for Claude, perhaps both on **one terminal emulation module**. My opinion, for the discussion:

- **The terminal emulator is a good fit and worth doing**, in this shape: a module `vt.[ch]` (no SDL, like `ansi.c`) that is the *model*: a state machine that eats bytes (VT100 / xterm subset: cursor movement and addressing, erase, insert / delete of characters and lines, scroll regions, `SGR` with 16 / 256 / true colors, the alternate screen, `DECSET` modes for the cursor and the mouse reports, `OSC` titles) and writes into a text screen through a small callback table; and a **pty front end** (`forkpty`, a child shell, resize with `TIOCSWINSZ`, `SIGCHLD`). It is testable without a window (`vttest1`, like `ansitest1`: byte streams in, cell contents out). The keys need no new code: `keyseq.c` already makes the canonical xterm sequences, which is what a pty wants. The text screen has runtime sizes since the console host, and the screen driver table (`scrdrv.h`) can carry it: a new screen (`TXTSCR_NSCREENS` 3 to 4) entered with a statement or key (an extension word: `TERM`?) and left with a key that the Engine keeps for itself. A BASIC-level cousin falls out of it: a `pty:` driver, like `sh:` but interactive (`OPEN "pty:bash" ...`).
- **The Claude screen should not be a second big feature at first.** The cheap, honest version is **the terminal emulator running `claude` (Claude Code)**: the integration is then a command line, and everything it needs (streaming, markdown, tools, the login) is somebody else's code. A native chat screen would need TLS (the `tcp:` driver has none: a new dependency, or a helper process), the API with streaming, JSON, key handling, markdown rendering in an 80 x 25 text screen, tool calls and, above all, **permission questions** (an AI that edits and runs programs on the user's machine): that is a project of its own. So I would **share the module only in the sense that the Claude screen is a client of the emulator**, not a second implementation of terminal handling. A chat screen that just prints text needs `ansi.c`, not a terminal.
- **Things to decide first** (*decision*): (1) the **character set**: the font is ISO-8859-15 with control glyphs; real terminal programs speak UTF-8 and use box drawing, block elements and arrows, which the font lacks (a second glyph page, or a mapping of the box drawing characters onto redefined characters, or accept `?`); (2) the **window size**: the window is a fixed 80 x 25 text screen; the emulator wants more (a resizable text screen on a bigger layer, or scrolling windows), and `htop` or `vim` at 80 x 25 are fine, a wider one is better; (3) **security**: a shell inside a program-controlled window is shell access; it must be opt-in and go through `iodev_allowed()` (item 3, sandboxing), and a `BUILD` executable must not get it silently; (4) the license exception and the dependency policy (no new libraries: `forkpty` is in glibc's `libutil` / `libc`, fine); (5) in the console host the emulator is a terminal in a terminal, useful for little: window host first; (6) whether a Claude screen needs a network permission and a place for the API key, and what the user is told before anything is sent anywhere.
- **Order**: the joystick (item 4) first; then `vt.[ch]` with its test and the `pty:` driver (useful by itself, small); then the emulator screen; then the `claude` launcher as a convenience on top. A native Claude chat screen only if the CLI turns out not to be enough.

## 15. A UI subsystem *(owner's idea, 2026-11-01; steps 0-3 of the order below done 2026-11-04, see [ui-subsystem.md](ui-subsystem.md))*

The idea: a UI subsystem that renders on the graphics screen and takes mouse and keyboard input, so that developers can write GUI-like programs ("a single application", one program owning the screen). My opinion:

- **It fits the engine, and the era**: 640 x 300 pixels, 256 colors per layer, an 8 x 12 font, a mouse pointer that is already a sprite: that is GEM / Windows 3.1 / AmigaOS territory, which suits a "1999" machine. The pieces exist: `gfxcore` draws boxes, lines, text and blocks on a palette bitmap, `mouse.[ch]` has position, buttons, wheel and the pointer shapes (hand, text, size arrows, wait, ... were drawn for exactly this), the key sequences reach `INKEY$`, `GFX GRAB` / `PUT` can save what is under a pop-up.
- **Shape**: a **C module `ui.[ch]` without SDL** (so it can be tested headlessly on a `gfxcore` bitmap, `uitest1`, pixel checks like `gfxtest1`): a retained widget tree (window / panel, label, button, check box, radio button, text field, list, combo / menu, scroll bar, slider, progress bar, tab, dialogs), hit testing, focus and Tab order, redraw of the changed parts only, a theme (palette entries and metrics). It is driven once per frame with the mouse state and the keys, and it queues **UI events** (widget id, kind: click, change, select, close, key). The BASIC side is small: a few statements and functions through one **extension word** (`UI`, no new one-byte token), with the same table style as `gfxops.c`, plus **`ON UI GOSUB`** (an event slot like `ON MOUSE`) and `UI("EVENT")`-style functions for a polling loop. Forms can be **defined by DATA / strings**, in the spirit of `DESIGN` (definition by picture), so that a dialog is a few lines of text.
- **Alternative worth weighing**: write the library **in BASIC** (`PROC`s, arrays, `ON MOUSE`, `MERGE`) as a shipped file. Zero C, shows what the language can do, easy for users to change; but it is slow in the VM (a button redraw is dozens of statements), has no real hit-testing structure, and every program pays the compile time. I would take the C core for the widgets and keep a BASIC library only for things built on top (dialog helpers, file requester, a color picker).
- **What the mouse and key subsystems still lack for it**: **motion events** (`ON MOUSE` has presses, releases and the wheel only; the UI polls `mouse_get()` per frame, so that is cheap and needs no VM change), **double click and click-and-drag with capture** (the UI can do both from the polled state), **focus** and key repeat for held keys (`KEY()` gives the state; repeat is the UI's own timer), and **key-up events** (`ON KEY`, roadmap item 4: not needed at first). The **joystick** (the next item) could drive the focus (D-pad moves it, a button clicks), a nice use that costs little if it is kept in mind from the start.
- **Things to decide first** (*decision*; the ones marked decided below were settled on 2026-11-01, see the next bullet): (1) **layer and palette**: the UI draws on the graphics layer (`GFX TARGET 3`?) that programs also draw on: does it own it (a "single application" says yes: the UI layer is the program's screen) or sit on its own layer above; it needs a reserved block of palette entries for the theme, or its own palette; (2) **windows**: begin with one screen of widgets (a form) plus modal dialogs and pop-up menus, and add overlapping, draggable windows later; (3) **retained or immediate mode**: retained is what I propose (state lives in the C module, the program reacts to events); immediate mode (`IF UIBUTTON("OK") THEN ...` every frame) is far easier to use from BASIC but redraws everything every frame; the two can share the drawing code; (4) **fonts**: one 8 x 12 font today (a second, proportional one is on the roadmap and would make text fields much nicer); (5) **the console host**: no graphics layer there, but the same widget tree could have a **text screen renderer** (the console host has mouse and keyboard in screen mode): a TUI from the same program. It doubles the rendering work, so later, but the module should keep the renderer behind a small table so that it stays possible; (6) the name and the words (`UI` as an extension word; the widget kinds are sub-keywords, as for `GFX`).
- **Decisions taken by the owner, 2026-11-01:** (1) **the UI owns the graphics layer** (no extra layer to composite, less rendering work; the UI's theme gets a reserved block of palette entries, programs that use the UI leave the graphics layer to it; the sprite layer with the mouse pointer stays in front); (2) **windows: first one form plus modal dialogs and pop-up menus**, overlapping windows later; (3) **retained widgets** (the state lives in the C module, the program reacts to events); (4) **a separate font engine for the UI layer with proportional fonts** (for buttons, labels and text fields: see below); (5) **the console host gets it too** (a text screen renderer behind the same widget tree; keep the renderer behind a small table from the start).
- **The font engine** (my notes on decision 4): a module `font.[ch]` without SDL, separate from the 8 x 12 text screen font, which stays as it is (the text screen is a grid of cells). It holds a font as glyph bitmaps with a width per glyph, ascent / descent / line height, and offers `font_measure()` (width and height of a string: layout needs it first), `font_draw()` onto a `gfxcore` palette bitmap (foreground index; background transparent or opaque; clipping) and character set conversion (ISO-8859-15 like the rest of the Engine). **No FreeType**: no new library, the Engine keeps its own fonts as bitmaps (a text source like `8x12font1.txt` and a generator like `fontcomp.pl`, or a small binary format loadable from a file through the I/O drivers, so that programs and users can bring fonts of their own). A few sizes of one or two built-in families (a sans for buttons and labels, a bold variant, perhaps a small one for status text), drawn by hand in the style of the existing font. No kerning, no anti-aliasing at first (with 256 palette entries per layer an anti-aliased font needs gradient entries between the text and the background color: possible later as a theme feature). It is useful beyond the UI: **`GFX TEXT` with a proportional font** and measuring from BASIC (`GFX("TEXTWIDTH", ...)`-style query) come almost for free, and the UI needs it before anything else because every widget's size follows from its text. **Test**: `fonttest1` (widths, measuring, clipping, drawing pixels on a `gfxcore` bitmap).
- **The text screen renderer for the console host** (decision 5): the same widgets drawn with box drawing characters and cell colors on a text screen (window and terminal), the mouse through the existing reports; a proportional font is not meaningful there, so the layout needs a metrics table that the renderer provides (cells in one, pixels in the other) rather than fixed pixel sizes in the widgets.
- **Order**: after the joystick: (0) `font.[ch]` and `fonttest1` (the font engine and a first proportional font), (1) `ui.[ch]` core with a theme, buttons, labels, check boxes, text fields, lists, and `uitest1`; (2) the BASIC statements and `ON UI`; (3) a demo (a form, a dialog, a menu) and a file requester; (4) the **built-in sprite and tile editors** (item 7) written on it: they need exactly these widgets (palette picker, buttons, a drawing area, scroll bars) and would be its showcase and its test; (5) overlapping windows and the text renderer if there is a wish for them.

## 16. Library support *(owner's idea, 2026-11-03; **done 2026-11-03**; design and what was built: [library-support.md](library-support.md))*

Revised the same day after the owner's decisions: programs load libraries with **`LOAD LIBRARY "name"`** (no `USE`), and **the user never types it at the prompt**: it is a declaration that the compiler resolves while `RUN` compiles (a pre-pass over the program's tokens finds the names, the libraries are compiled into the same code and data segments *before* the program, so their `FUNC`s are known to the parser; at run time the statement does nothing). A library is an ordinary program file whose first statement is `LIBRARY "name"[,"prefix"]`; only `PROC` / `FUNC` / `DEF FN` / labelled sections and `LOAD LIBRARY` are allowed in it; it cannot be run; plain `LOAD` still works for editing it, so **the file format does not change**. Line numbers are local to a library, names are global (clash = compile error), run time errors name the library, variables follow `LOCAL` + a prefix and anything else is a compile error, the runtime calls `<prefix>INIT`, `DATA` is allowed (unlabelled = private to the library, per-module chains and READ pointers), `SAVE LIBRARY` writes the optional `.lib` / `.l99`, `LIBRARIES` lists the loaded ones, `BUILD` embeds the libraries in a container. Search path: current directory, `lib/`, the program's own directory, the installed `lib/engine1999/lib/`. The plan (7 steps) is in the design document; **the owner settled decisions a to g on 2026-11-03** (recorded there).

## 17. Ideas of 2026-11-03 *(the owner's `ideas-and-suggestions.txt`; nothing decided or started unless noted)*

- **Sprite paths** (item 52): every sprite gets an optional path string that the engine runs per frame like a `PLAY` string runs per note (the screen thread already moves sprites for `MOVETO` and animations, so no BASIC time is used). The owner's words: `X+3` / `X-3` / `Y+3` / `Y-3` move, `R` repeats from the start, `W3` waits 3 frames, `A3` switches to animation 3, `E3` triggers event 3. *Questions* (*decision*): a move needs a duration or it is a single jump: I suggest `X+3*20` = 3 pixels per frame for 20 frames, and plain `X+60` = 60 pixels spread over `T` frames (a `T n` command, default 1); absolute `X=100` / `Y=50`; `[ ... ]n` repeat n times (nesting 4); `H` / `S` hide / show; `Pn` priority; `Dn` set the image; `J` n jump to command n; **`E3`** should feed the existing event system (like `ON COLLISION`: an event slot, `ON SPRITE GOSUB`, the sprite number and the event number readable by `SPRITE("EVENT")`). Syntax: `SPRITE n,PATH a$` and `SPRITE n,PATH OFF`; the string is parsed completely first (errors at once, like `PLAY`); the sprite state keeps a program counter. The reserved sprites 248..255 can use paths as well (an animated mouse pointer needs none; the pointer is moved by the mouse module).
- **Speech synthesis** (item 57, Low): like AmigaOS `narrator.device`: `SPEAK a$` (phonemes or words), `SING` later; voices male / female / robotic as speaker definitions (presets and a statement). My opinion: **do not take a library dependency** (the engine has none besides SDL2); a formant synthesizer in `synth.c`'s style (a source-filter model: a buzz or noise source into a few resonant filters, driven by a phoneme table) is a self-contained, few-hundred-line job and gives the right 1980s sound. English words by a small rule-based text-to-phoneme table (the 200 most frequent words as a dictionary, the rest by letter rules); other languages later. Singing = pitch and duration per phoneme taken from a `PLAY`-like string.
- **Audio tracker** (item 56, Medium-Low): an editor on the text screen (pattern grid, channels as columns, rows of notes / instrument / volume / effect) that plays through `PLAY` strings and `SFX` / the synthesizer's events and can print the resulting strings (so it doubles as the discovery tool for `PLAY` strings); later a score view (Sonix / Musicraft style) for 8 voices. Best done as a BASIC program on top of the libraries (section 16) first, to see what the language still lacks.
- **Security policy** (item 54, refines section 8's sandboxing): default policy for all I/O and shell access = **relative paths below the application directory only** (never up, never absolute). When a program breaks it at run time a dialog says so ("This program tries to scan files outside of its folder. Allow?", with the literal command for a shell literal); on yes a second dialog asks how long to remember ("this session", "today", "always"), stored under the user's `.config` / `.local` directory. Programs may ask for permissions upfront by a file next to the program (like Java's policy) or by command line options; the user is asked at start and the answers are handled as above. *Notes*: `iodev_allowed()` is already the one hook; the console host has no dialogs, so there the question is asked on the terminal (or the default is *deny*, with `--allow ...` options); dialogs in the window need the UI subsystem (section 15) or a minimal SDL message box (`SDL_ShowMessageBox`, no dependency) first; the grant store must be keyed by the program's path and a hash of its content, or a changed program inherits the old consent.
- **Game "Eternal River" / "Go With The Flow"** (item 55): a scroll-down boat game. Fits the engine as `climb.bas` and MADRUN do (scrolling by `TILE FILL`, the world generated from a seed, sprites for the boat, swimmers, divers, other boats; bridges with decorative traffic as sprites with paths once item 52 exists; the diver who falls off swims, reaches the bank, walks until a boat is found). Collect: fruit, vegetables, ice cream. Death by collision or rock (luck). A demo, after the libraries.
- **BMP files and asset files** (item 53): *BMP*: reading palettized 1/4/8 bpp (convert to 8 bpp, match the colors to the layer's palette entries) and 16/24/32 bpp (map each pixel to the nearest palette entry; an alpha channel becomes entry 0 = transparent); writing: 1/4/8 bpp synthesize the palette from the pixels (reduce the colors when there are too many), 16 / 24 bpp convert to the nearest representation, 32 bpp stored as it is. Statements in the same style: `GFX LOAD a$[,x,y]` / `GFX SAVE a$[,x1,y1,x2,y2]` (the graphics or background layer), `SPRITE LOAD a$,first,w,h` (a sheet cut into sprite images), `TILE LOAD`, `TILE MAP LOAD` / `SAVE`, and `PALETTE LOAD` / `SAVE`. *Suggestion*: BMP for pictures and sheets (any tool can edit them), plus one small own container later (`.spr` with images, sequences and palette) for whole sprite sets (item 20). Everything goes through the I/O drivers (`mem:` works too), in the 4-byte-header style that `GFX GRAB` strings already use.
- **Demo scene programs** (item 58, Low): *are we there yet?* Partly: palette cycling, per-pixel drawing, sprites with priorities, tile scrolling, `SIN` / `COS`, `RND`, music and `FRAME` exist. Missing for a 1999 style demo: (1) **fast pixel work**: a way to move a block of bytes between a string / the RAM and a layer (`GFX PUT`/`GET` exist for blocks; a `POKE`-able window onto a layer's bitmap would give plasma and tunnel effects) and a faster interpreter loop for tight pixel loops; (2) **raster effects**: a per-scanline palette or scroll offset (raster bars, wobbling logos, split screens), which needs a hook in the renderer; (3) **sine scrollers / rotozoomers**: a `GFX BLIT` with a scale and rotation; (4) timing: a demo clock in milliseconds. It is a good stress test for the engine; the first two are the valuable ones.
