Ideas to put on the roadmap or to amend or expand existing entries:

- library support: Please make a suggestion how to implement it. Perhaps any BASIC program could be loaded as a library using LOAD LIBRARY n$ . The library's first statement would be LIBRARY "name", and the loader would check it. When LIBRARY "..." occurs, the compiler would switch into library mode. In a library, only FUNC and PROC sections, and labelled code sections are allowed (no other code between FUNC and PROC sections, if it's not labelled, the compiler would check it). SAVE [LIBRARY] n$[,flags] would save it. A library by itself cannot be run (error "Library cannot be run"). During LOAD LIBRARY n$, the loader would check if it's a library. If not, it would output an error and stop. If it's a library, the BASIC source code would be loaded into a temporary area for compilation. Code and data would end up in the current program's code and data areas, so the VM can access it. Thus, FUNCs, PROCs, and labelled areas should become accessible to the current program. Does this suggestion make sense? Put it as highest priority on the roadmap, since it would allow us to share code between our demo programs.

- The default security policy for all I/O and shell access should be "relative paths from the application directory (never up, only down) only".
- When a program attempts to break this policy at runtime, the user should see a dialog box in the spirit of "This program attempts to scan files outside of its assigned folder. Do you want to allow this?" (perhaps with the literal statement that the program tries to run) - If the user agrees, they should see another dialog box with something like "Remember this choice?" with choices like "the current session", "only today", "forever" - what they choose should be stored in an appropriate place (in their .config or .local directory for instance).
- A program can request permissions either by using a file next to the executable (similar to Java) or by specifying command line options. When the program starts, the user is asked to grant those permissions. The handling should be the same as when it tries to break policy. The only difference is that the user is asked upfront.

- A game like River Raid (perhaps called "Eternal River" or "Go With The Flow") as a scroll-down boat game. The player is in a boat in a river that is meandering while scrolling down. They need to avoid swimmers and divers, and other boats. Occasionally there should be bridges over the river with people, bicycles or vehicles walking over them, but it's just for decorative purposes. The banks of the rivers should be lined with grass, trees, houses and roads. (Not sure if this is feasible) At the banks, there should be occasional people throwing rocks at the boat. If the diver is thrown off the boat, they should be able to swim. If they reach the banks, they should be able to continue walking until they find another boat. On the banks, there should be occasional things to collect, like fruit or vegetables, or ice cream cones. The player dies randomly if they collide with a boat or hit by a rock, so it'll be a case of luck if they'll be able to swim.

- Support of Microsoft BMP files (should be easy to implement and permissible since the ECMA standard for Windows 3.1): During loading, palettized files should be converted to 8bpp and their colors matched to existing palette entries. For 16, 24 and 32 bit colors, the pixels should be mapped to palette colors. During saving, the reverse should happen: For 1,4,8 bpp, the palette should be synthesized from the pixels and the image color reduced while doing so. For 16,24,32 bpp, the pixels should be converted to the nearest approximation (esp. 16bpp, 24 bpp loses alpha channel, 32 bpp stored literally).
- After implementing that, there should be support for sprite and sprite map load and save, background load and save, tile map load and save, tile load and save. Feel free to suggest something more suitable.

- Are we there yet for making "demo scene" programs? From around the year 1999 would be sufficient. Low priority.

- A potential bug: Sometimes when starting engine1999, its screen opens in the background. Any idea why this happens? If not, we should add some code at the beginning of the program to attempt to bring it into foreground first if it isn't (this could be tried for up to 1-3 seconds). High priority.

Important new rule to add: Do not make breaking changes to the ABI (i.e. *.E99 format), so users can trust that a program saved will always load back currently (you have a version number in the E99 format for that purpose, bump the version if you make a breaking change. The engine should then keep supporting the old formats / version numbers for LOAD). An optional addition to that would be to make the default SAVE format ASCII (A), since nowadays, people would be more likely to expect that. 

Another rule to add: Unlike C++, in C, variables that go into the BSS segment of an executable (uninitialized variables), are NOT set to zero automatically. When writing new code, always check for uninitialized variables and explicitly set them to zero. Likewise, malloc(), unlike calloc(), always return an uninitialized data block. Memory exposed via realloc() is also not initialized. Always set affected memory regions to zero before using them.
